  fixed-price and RFQ coordination, payment rails, seller lifecycle primitives,
  registry selection and substrate helpers. `demosTransactionContentMatches`

  from [#368](https://github.com/DACS-Agent-commerce/dacs-sdk/pull/368) are merged.

  recovery and wallet authority integrations, and the Demos loader entry point.

  dependency versions. Its generated projects are a separate dependency graph;
  the generator itself declares neither package as a runtime dependency.

  keeps purchases held. Its merge does not make it a public, usable package.
- `Agent.runSession()` remains a settlement-only compatibility API. Use the
  role-separated fixed-price coordinators for fulfilment and audit; completion
  of that legacy method does not establish a completed commerce lifecycle.

### Pending payment change: breaking for custom clients and reconcilers

The planned native DEM flow requires a transaction record that establishes
execution. Inclusion by itself will leave settlement, delivery and accounting
pending. These migration notes summarize the pinned SDK source proposals above:

- Build rails with `createPayDemRail` and pass them unchanged. Caller-built
  `DemosNativeClient` instances and wrapped/custom rails will no longer qualify
  for fresh settlement; refusal happens before a transfer or wallet reservation.
- A `PayDemSettlementReconcile` success must establish the bound confirmed
  record and carry `execution: "executed"`. Handle audit contexts for the exact
  retained `txHash`; recovery cannot replace that transaction with a new send.
- Durable logs need `readOutcome`, `putAttempt` and `readAttempt` together.
  Pass the resulting `createIdempotencyStore` store with its read capabilities.
  Restore the rail log with the session store; session history alone does not
  establish ownership of the original transaction. A recorded but unsent hash
  can remain held for operator review.
- Saved native successes and evidence are reauthenticated on resume. The
  original recovery capability and prepared-transfer journal are required.
- Custom observation providers must use `observePayDemTransferCore` with their
  authenticated `PayDemObservationClient`. Only the SDK observer's original
  executed observation carries its attestation; copying it loses that identity.
- Completed V1 buyer reconciliation must return executed status, the signed
  nonce and the checkpoint's confirmed fee as `networkFeeOs`. The SDK rail's
  record reader must independently confirm the nonce, block and fee. Missing
  or conflicting fee evidence leaves accounting held for operator review.
- Buyer audit retries unavailable or inclusion-only observations. Applications
  must preserve pending states instead of reporting them as terminal rejection.

## Release preparation and remaining gates

Run `npm ci --ignore-scripts --no-audit`, `npm run release:test`, then
`npm run release:dry-run`. The preparation dry-run reports missing, private or
the explicitly listed source blockers as **not ready**. Packages with build scripts
are built; every present package is packed and file-checked. Archives with only
known blockers are also dry-run. Dependency, identity, version, internal-pin and required-export
checks run independently on both source and packed manifests. Unexpected manifest
defects fail preparation. The policy pins the held private client's exact manifest
and file inventory for preparation only. Its absent release metadata/exports and
`0.0.0` version are explicit snapshot exceptions; a changed manifest must satisfy
the normal checks. These exceptions do not extend its public release allow-list.
The preparation command succeeds when the report completes; build, archive,
file-policy and npm dry-run failures still fail the command. It prints the
planned target, actual manifest versions and declared internal dependency edges.
No version changes are applied: today's output describes alpha.0 and held `0.0.0` artifacts.
No publication credentials are needed.
Default regressions use local native-driver fixtures; `npm run release:test:native`
separately qualifies the real registry driver.

`npm run release:check` remains the strict release gate. It requires all five
packages at the planned version, exact internal runtime/peer/optional pins, registry
specifications (including development dependencies, overrides and resolutions),
MIT licensing, the canonical repository, public access and provenance. It checks
packed files and concrete wildcard export/type pairs, installs the supplied
internal tarballs and checks each public entry in a clean consumer. Packed
versions must equal the admitted source versions, and packed internal pins are
checked again. Registry aliases targeting internal packages are refused; external
registry aliases remain supported. Export exclusions follow Node specificity.
The packed generator must report its own version and generate offline and live
projects whose internal dependency pins and generator metadata match the artifacts. An incomplete
set cannot pass even when its surviving subset installs successfully. Packed-only
blockers are recorded in the final result, and strict success independently
requires exactly one publicly releasable artifact for each of the five identities.

PR, main and merge-queue CI run the regression tests and preparation dry-run on
Node 20.19 and 22.21 with the publisher's `npm@11.19.0`. A manual Package artifact
workflow run additionally requires `release:check` on both Node versions.

The clean consumer first omits optional dependencies and imports the Node kit's
non-SQLite entries with `better-sqlite3` absent. It then explicitly installs
`better-sqlite3` at the Node kit's exact manifest pin (currently `12.6.2`). Both
installs disable every lifecycle hook; only that exact native package may rebuild.
An in-memory query verifies the native binding before all public imports,
including the Node kit root and `./sqlite`.
On Node 20, the planned seller and client durable journal may be labelled not
imported only for the expected `node:sqlite` rejection. Every other import
failure fails the strict gate on either Node version. This smoke does not replace
the existing SQLite migration and generated-project acceptance checks.

Consumer lock resolutions must use `https://registry.npmjs.org`; alternate
registries require a reviewed policy change. External peers are installed
explicitly from their declared registry specs for
the full public API smoke. Those specs and transitive dependency ranges deliberately
test a fresh registry install. Strict checks preserve each consumer lockfile,
resolved dependency inventory, supplied artifact SHA-512 hashes and Node/npm/
platform identity under `package-artifacts/five-package/node-<version>/run-<id>/` before
scratch cleanup, including diagnostics when an import fails. Each run has a
separate result file so incomplete and older evidence cannot be confused. Manual workflow
runs upload this evidence. It records the graph actually checked; it does not
bind future runs to that graph. The source build uses `npm ci`; the existing
reproducible-package and release-set checks remain responsible for exact
artifacts and SBOMs.

Today's readiness blockers include the held private client's missing release
metadata and exports, the absent seller, the Node kit's `file:../..` development
dependency, and versions below the planned alpha.1 release. Rejecting development
links is an explicit release policy: resolve that packaging link in a reviewed change before
release. The native binding smoke above establishes basic SQLite availability;
it does not qualify migrations, recovery or application behavior.
Pending documents and vectors must be added to the file policy when their actual
contents are reviewed; they are not pre-approved here.

Before the actual release: merge and qualify the pending work; finalize the
supported APIs, file policies and release notes; set all five versions, internal
