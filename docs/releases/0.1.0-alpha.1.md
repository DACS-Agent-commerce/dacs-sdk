  registry selection and substrate helpers. `demosTransactionContentMatches`

  recovery and wallet authority integrations, and the Demos loader entry point.

  dependency versions. Its generated projects are a separate dependency graph;
  the generator itself declares neither package as a runtime dependency.
- The client snapshot from [#366](https://github.com/DACS-Agent-commerce/dacs-sdk/pull/366)
  keeps purchases held. Its merge does not make it a public, usable package.
- `Agent.runSession()` remains a settlement-only compatibility API. Use the
  role-separated fixed-price coordinators for fulfilment and audit; completion
  of that legacy method does not establish a completed commerce lifecycle.

### Pending payment change: breaking for custom clients and reconcilers

The planned native DEM flow requires a transaction record that establishes
execution. Inclusion by itself will leave settlement, delivery and accounting
pending. These migration notes paraphrase the linked PR bodies above:

- Build rails with `createPayDemRail` and pass them unchanged. Caller-built
  `DemosNativeClient` instances and wrapped/custom rails will no longer qualify
  for fresh settlement; refusal happens before a transfer or wallet reservation.
- A `PayDemSettlementReconcile` success must establish the bound confirmed
  record and carry `execution: "executed"`. Handle audit contexts for the exact
  retained `txHash`; recovery cannot replace that transaction with a new send.
- Durable logs need `readOutcome`, `putAttempt` and `readAttempt` together.
  Pass the resulting `createIdempotencyStore` store with its read capabilities.
  Restore the rail log with the session store; session history alone does not
  establish ownership of the original transaction. A recorded but unsent hash
  can remain held for operator review.
- Saved native successes and evidence are reauthenticated on resume. The
  original recovery capability and prepared-transfer journal are required.
- Custom observation providers must use `observePayDemTransferCore` with their
  authenticated `PayDemObservationClient`. Only the SDK observer's original
  executed observation carries its attestation; copying it loses that identity.
- Completed V1 buyer reconciliation must return executed status, the signed
  nonce and the checkpoint's confirmed fee as `networkFeeOs`. The SDK rail's
  record reader must independently confirm the nonce, block and fee. Missing
  or conflicting fee evidence leaves accounting held for operator review.
- Buyer audit retries unavailable or inclusion-only observations. Applications
  must preserve pending states instead of reporting them as terminal rejection.

## Release preparation and remaining gates

Run `npm ci --ignore-scripts --no-audit`, `npm run release:test`, then
`npm run release:check` and `npm run release:dry-run`. Both release commands
inspect all five packages and fail if one is absent, private or missing exports.
The dry-run prints the planned target, actual manifest versions, declared
internal dependency edges and npm's dry-run output for each available tarball.
It does not apply version changes; its output currently describes alpha.0
artifacts. No publication credentials are needed.

CI uses Node 20.19 and 22.21. Node 22 requires every entry to import. The planned
seller and client durable journal require Node 22.13+, so Node 20 checks their
`node:sqlite` rejection; other import failures still fail the job. Native
optional dependencies are omitted, and declared peers are installed explicitly
for the full public API smoke. This does not replace the existing SQLite and
generated-project acceptance checks.

The check also rejects the Node kit's current `file:../..` development dependency
in its manifest. That packaging link needs a reviewed resolution before release.

Before the actual release: merge and qualify the pending work; finalize the
supported APIs, file policies and release notes; set all five versions, internal
pins and generator constants from one release version; qualify the exact packed
composition; record the dependency assessment and dispositions associated with
[#191](https://github.com/DACS-Agent-commerce/dacs-sdk/issues/191); prepare the
five-package SBOMs and receipts; and obtain the required release approvals and
publication credentials. The existing real publisher still handles three
packages and requires a separate reviewed five-package update. The experimental
testnet profile does not claim production readiness or full Standard conformance.
