# Walkthrough: a generated live project on testnet

This page walks through a project generated by `create-dacs-agent --mode live-demos --rails x402`,
on one host, with test wallets, on Base Sepolia and the Demos testnet. Steps 8 and later, including
the buy's doctor and its blocked checks (`x402.service-limit`, and `x402.asset-balance` until the
buyer holds test USDC), are described from the code and not run on testnet. **It does not run a funded purchase.**

Each step is marked **script** (run by `scripts/fixed-price-x402-walkthrough.mjs`), **manual** (you
run it) or **not run** (documented from the code, never run end to end). The commands and output
shapes are taken from the script and from the code of the generated project. This page does not claim
that any step passed on testnet.

Directories matter. The script exists only in the checkout, so each `node scripts/…` command runs in
`<checkout>`. The generated project's `npm run dacs:…` commands read `./.env`, `./request.json` and
`dist/` of the project, so they run in `<run>/project`. Each block below starts with the `cd` it
needs, and `<run>` is an absolute path.

The script has three commands, each with `--run-dir <run>`: `init`, `registry` and `record`. It has
no help text; the usage is the comment at the top of the file, and an unknown command (`--help`
too) prints `unknown command: <name>`. On any failure the script prints one message and exits 1.

## What does not work yet

- **The buy's doctor blocks, by the code (not run).** `dacs:buy` prints no plan line unless its own
  post-start doctor passes. Two required checks of that doctor block on the project `init`
  writes, one of them until step 3. `x402.service-limit` is always blocked, because the buyer points at a placeholder wallet
  authority with nothing behind it. `x402.asset-balance` is blocked unless the buyer's EVM address
  holds test USDC (step 3). So step 9 exits 5, or 1 if another required check fails, with no plan
  line, after setup, and `record --listing-ref` then reports the `buy` step as `blocked`
  and the `setup` step as `unrun`.
- **The funded purchase is unrun.** The repository has no runnable wallet-spend authority service, and
  the buyer reads the seller only over public HTTPS from a public address.
  - The generated buyer always asks a separately operated wallet-spend authority before it pays.
    The server side, `createDacsWalletSpendAuthorityServiceV2`, is called only from tests in this
    repository. `init` writes an unpayable placeholder (the loopback URL of a port with no service
    behind it, a random token, and a random witness key whose private half is never created), so the
    buy check `x402.service-limit` cannot pass.
  - The buyer refuses `localhost` and any non-public address when it reads the seller's Listing and
    result. The seller URL must be public HTTPS for a buy to get that far.
- **A role service starts not ready.** A role service started on its own refuses messages and does no
  work until the project's post-start doctor has checked both roles and signed a readiness record for
  each. That doctor needs the buyer and seller keys in one process; there is no way yet to make one
  role ready by itself. A readiness record lasts five minutes, and nothing renews it automatically.
  Rerun the post-start doctor after every start, right before a buy, and at least every five minutes
  while an order is in progress. A confirmed `dacs:setup` runs that doctor itself before it writes.
- **The generated project ships no Listing draft and no signing step.** The script's `registry`
  command writes the draft and signs the seller identity with the seller's key.
- **The rail registry bootstrap is a script step and fixes the seller URL.** The generator has no
  bootstrap. The URL you pass to `init` is registered for that seller key for good, and the Listing
  must match it. Another URL means a new run directory and new wallets.
- **Packages come from the checkout.** The generated project pins the generator's own version
  exactly. Step 1 packs the checkout's own packages into `<run>/packs` and installs those tarballs, so the project
  runs the code of the checkout. `init` refuses a project whose installed packages are not at the
  checkout's version.
- **Metrics are telemetry.** `dacs:metrics` timings are operational, not protocol proof.

## Before you start

- Node `^22.22.2` or `^24.15.0`. `init` refuses any other version, and Node 25 and later does not
  work with the Demos SDK (`docs/live-e2e.md` §1).
- A git checkout with no tracked changes (`git status --porcelain --untracked-files=no` must be
  empty). `init` refuses otherwise.
- A persistent run directory outside the checkout, created by step 1 with mode `0700`.
- A public HTTPS URL with a path for the seller, such as `https://host.example/seller`. A root path is
  refused. `init` and `registry` do not contact it.
- An HTTPS Base Sepolia RPC URL of your own. `docs/live-e2e.md` §3 lists public ones. Use a URL
  without a provider key for this walkthrough where one exists. `init` takes the URL only as
  `--evm-rpc <url>`, with no environment variable, so the URL reaches your shell history and the
  process arguments of the `init` command, and `init` also writes it to `project/.env` (mode
  `0600`). A provider key in the URL reaches all three. `record` writes the EVM RPC host
  as `custom` (see "Before you share").
- Network access to the npm registry, the Demos RPC (default `https://node2.demos.sh`), the Demos
  faucet (`faucetbackend.demos.sh`), your Base Sepolia RPC and the facilitator
  (`https://x402.org/facilitator`).
- Testnet only. Use disposable test wallets. Never commit keys or `.env` contents, or paste them
  into an issue or log.

Funding follows `docs/live-e2e.md` §2 for the faucet requests and the DEM denomination.

## Steps

### 1. Build and generate (manual)

These commands follow the flow of the packed live consumer job in CI, but generate the project with
`--role seller --deploy local` where that job uses `--role buyer --deploy docker`. `<checkout>` is
your checkout, `<run>` the run directory, and `<v>` the checkout's version
(`node -p 'require("./package.json").version'`).

```bash
mkdir -m 700 <run>                         # refuses a directory that exists
mkdir <run>/packs <run>/runner
cd <checkout>
npm ci
npm run build
npm run host:build
npm run generator:build
npm pack --pack-destination <run>/packs
npm pack --workspace @kynesyslabs/dacs-node --pack-destination <run>/packs
npm pack --workspace create-dacs-agent --pack-destination <run>/packs
npm install --prefix <run>/runner --no-audit --ignore-scripts <run>/packs/create-dacs-agent-<v>.tgz
node <run>/runner/node_modules/create-dacs-agent/dist/bin.js <run>/project --yes --mode live-demos \
  --profile dacs-sdk:fixed-price-x402:v1 --rails x402 --role seller --deploy local --no-install
cd <run>/project
npm install --no-audit --no-save --ignore-scripts --omit=optional \
  <run>/packs/kynesyslabs-dacs-<v>.tgz <run>/packs/kynesyslabs-dacs-node-<v>.tgz \
  typescript@5.9.2 @types/node@20.19.1
npm rebuild better-sqlite3
npm run typecheck && npm test
```

- **Output.** The generator prints `Created <dir>`, `Profile: …`, `Installed: no`,
  `Ran verifier simulation: no` and `Doctor: not-run`. The doctor runs only after an install.
- **Needed later.** `<run>/packs` must hold exactly the three tarballs and nothing else. `npm test`
  builds the project, and `init` needs the built `project/dist`.
- **Can fail on** npm registry access for third-party dependencies, or a project directory that is not
  empty.

### 2. Wallets and configuration (script)

```bash
cd <checkout>
node scripts/fixed-price-x402-walkthrough.mjs init --run-dir <run> \
  --seller-url https://host.example/seller --evm-rpc <https-base-sepolia-rpc>
```

- **It refuses, before writing anything,** a run directory inside the checkout or not mode `0700`
  and owned by you; an unsupported Node; a `<run>/secrets` that exists or a `state.json` that records
  `init`; a `project/.env` or `project/request.json` that exists; a project that is not built, not generated with
  `--mode live-demos --rails x402 --deploy local`, or not installed with both packages at the
  checkout's version; tracked changes in the checkout; a seller URL that is not plain HTTPS with a path; and an EVM chain id
  other than 84532.
- **It writes:**
  - `<run>/state.json`: the commit, the package version, the sha256 of each tarball, the registry
    inputs (the time, the USDC contract and the normalized seller URL);
  - `<run>/secrets/` and `<run>/logs/`, mode `0700`, with two Demos mnemonics and two EVM keys in
    `0600` files and the placeholder authority token. Keys never reach argv, env, stdout, logs or
    `state.json`;
  - `project/.env`, a copy of the generated `.env.example` with only these names set: both
    authorities, the rail steward (the seller), the seller's EVM payee, the five secret file paths,
    the wallet-authority settings of the placeholder, the seller URL, the facilitator, the EVM RPC
    URL, the Base Sepolia block number to search authorizations from, and a price and ceiling of
    `0.000001`. It never writes a `DACS_*_CONFIRM` value, and the project refuses one in `.env`;
  - `project/request.json`, the closed purchase request.
- **It prints** `init done. Fund both Demos addresses, then run registry:`, the buyer and seller
  addresses, and one faucet `curl` per address.
- **Can fail on** a pack directory with a missing or extra tarball, or an installed package whose
  version differs from the checkout's.

### 3. Fund the wallets (manual)

Run each printed `curl`. Do it **one wallet at a time**, and check that wallet's balance before you
request for the next: the faucet can accept a request and send nothing. If a wallet stays at zero,
start again with a new run directory rather than repeating the request. `dacs:setup` needs **both**
wallets funded. A request gives about 2,400 DEM, far more than a run needs.

The buyer's EVM address also needs test USDC (Base Sepolia, chosen explicitly on the faucet; see
`docs/live-e2e.md` §2), at least the `0.000001` that step 9 passes as its service amount. The buy's
doctor needs it for its `x402.asset-balance` check, which is blocked without it, and a funded
purchase would need it to pay. No ETH is needed: the gas check's minimum is zero. A funded purchase
is not run.

`init` does not print the buyer's EVM address. The code reports it as `facts.payer` of the
`x402.payer-binding` check in `npm run dacs:doctor -- --phase pre-start --for buy --json`, run in
`<run>/project` (this command is not run on testnet).

### 4. Rail registry and Listing draft (script)

```bash
cd <checkout>
node scripts/fixed-price-x402-walkthrough.mjs registry --run-dir <run>            # plan
node scripts/fixed-price-x402-walkthrough.mjs registry --run-dir <run> --confirm  # bootstrap
```

- **It refuses** to run while the seller service answers `/health`, so run it before step 6 (or after
  `dacs:down`). It runs inside the project and opens the seller's Demos runtime, which connects to the
  Demos RPC.
- **It first reads the rail with a read-only lookup.**
  - No rail and no `--confirm`: it prints the plan as JSON (`"rail": "plan"`, the steward, the seller
    URL, the asset, the logical addresses and the fee ceiling per write) and makes no Demos write,
    and saves no state and no draft.
  - No rail and `--confirm`: it makes the one bootstrap call, then continues.
  - A rail that exists: it makes no Demos write and continues, with or without `--confirm`.
- **It continues** only if the registered rail matches the URL and asset saved by `init`. It saves
  the registry refs and the Demos chain identity in `state.json`, and writes
  `project/listing-draft-x402.json` only if that file is absent. The seller identity in the draft is
  signed with the seller's key through the seller runtime. The draft holds public values and the
  signature only, and is never overwritten.
- **It prints** the summary as indented JSON over several lines (`JSON.stringify` with two spaces):
  `"rail"` is `"bootstrapped"` or `"existing"`, `"draft"` is `"written"` or `"present"`, and
  `"chainIdentity"` follows. The plan prints over several lines the same way.
- **Can fail on** too little DEM, a seller service already running, a rail that does not match, or a
  Demos write rejected because its reference block expired (see Troubleshooting). The raw output of
  the step is in `<run>/logs/registry.log`.

### 5. Pre-start doctor (manual)

```bash
cd <run>/project && npm run dacs:doctor -- --phase pre-start --for start
```

- It prints `dacs doctor`, the phase and scope, `gate: pass|blocked|fail`, one line per check,
  `report: <hash>` and `exit: <code>`. Exit `0` is pass, `5` is blocked and `1` is fail.
- A fresh project can exit `5` here; see Troubleshooting.

### 6. Start (manual)

```bash
cd <run>/project
npm run dacs:up
```

- `dacs:up` runs this pre-start doctor itself. If the only required checks that did not pass are
  `local.data-directory`, `local.disk-space` or `local.sqlite`, it creates both roles' stores and
  runs the doctor again. If other checks did not pass, it prints the report and stops with the
  doctor's exit code.
- Once the doctor exits 0, it prints the report, starts one process per role and prints
  `{"status":"started","deployment":"local","roles":[…],"readiness":"post-start-doctor-required"}`.
- Each service then answers `/ready` with 503 and `readiness-latch-missing`:
  `curl -s 127.0.0.1:3101/ready` (buyer) and `127.0.0.1:3102/ready` (seller).
- **Can fail** when a service does not answer `/health` within 30 seconds, for example because its
  port is occupied or it exits at start. `dacs:up` then stops the services it started, prints only
  `dacs command failed; rerun doctor for a sanitized diagnosis` on stderr, and exits 1. The cause is
  in the `service.log` in each role's data directory.

### 7. Readiness (manual)

```bash
cd <run>/project
npm run dacs:doctor -- --phase post-start --for start
```

- If every required check passes, the doctor commits a signed readiness record for each role, and
  both `/ready` answer 200 `{"ready":true,…}`. If one does not pass, it revokes both records. In
  both cases it prints the whole report, one line for every check (not only the ones that did not
  pass), and exits with the report's exit code.
- The record lasts five minutes. After that `/ready` answers 503 `readiness-latch-expired` until you
  rerun the doctor.

### 8. Listing setup (manual, not run)

```bash
cd <run>/project
npm run dacs:setup -- --max-spend-dem 10                          # plan
DACS_SETUP_WRITE_CONFIRM=1 npm run dacs:setup -- --max-spend-dem 10   # confirmed
```

What the code does:

- The plan prints one JSON line starting `{"execute":false,…` and exits 0.
- The confirmed run runs the post-start doctor (which also renews readiness), then the pre-start
  setup doctor, which checks the signed draft and stops on any check that does not pass. It then asks
  `Type yes`, unless `--non-interactive` is given, and prints the result with `listingRef`. Exit 0
  means `completed` or `existing-completion`; any other status exits 5, and you rerun the same command.
- Without a terminal and without `--non-interactive` it refuses.

### 9. Buy doctor and plan (manual, not run; described from the code)

```bash
cd <run>/project
npm run dacs:buy -- --listing-ref <ref> --request-file ./request.json \
  --max-service-amount 0.000001 --max-network-fee-eth 0.001
```

`<ref>` is the `listingRef` that setup prints. Rerun the post-start doctor right before it, because the buy runs the post-start buy doctor first and
a readiness record lasts five minutes.

- A passing doctor is followed by one JSON line starting `{"execute":false,"invocationMode":"new",…`
  and exit 0. Without `DACS_PURCHASE_CONFIRM` the command stops there and makes no write.
- A blocked doctor prints its report and exits 5 (or 1 on a failure), with no plan line.
- By the code, the doctor blocks on the project `init` writes. Its required `x402.service-limit` check asks
  the placeholder wallet authority, and nothing answers, so it is blocked whatever the wallets hold.
  Its required `x402.asset-balance` check is blocked while the buyer's EVM address holds less than
  the `--max-service-amount` value in test USDC (step 3). The step therefore prints no plan line and
  exits 5, or 1 if another required check fails. This page lists no other check ids, because no run has recorded them.
- **Do not set `DACS_PURCHASE_CONFIRM`.** That would enqueue a new job, which is a funded purchase.
  The job id in a plan line is not the one that runs.

### 10. Rerun and resume (not run)

Steps 10 and 11 need only the running services of step 6, not a Listing, so they can be reached any
time after step 6 (all `npm run` commands in `<run>/project`). Resuming a purchase and reading a
job's metrics also need the job id of a purchase, which this page does not run.

- A purchase is resumed only with `--resume-job <printed-job-id>` and the same inputs. A resume with a
  job that does not exist is refused with `purchase-resume-target-missing`.
- A fresh `dacs:buy` is a new job and a second payment. **Never use one to recover.**
- `npm run dacs:down` and `npm run dacs:up` is a clean restart. Services resume pending work from
  their stores once you rerun the post-start doctor.

### 11. Status and metrics (not run)

- `npm run dacs:status` prints the services' status as JSON. It exits 0 when both are available and 5
  otherwise.
- `npm run dacs:metrics -- --job <id>` prints each role's milestones and audit completion for a job.

### 12. Record and stop (script and manual; not run)

Rerun the post-start doctor (manual), then record and stop. `record` without `--listing-ref` and
`dacs:down` work even when step 8 fails, so stop the services after a failed setup:

```bash
cd <run>/project
npm run dacs:doctor -- --phase post-start --for start
cd <checkout>
node scripts/fixed-price-x402-walkthrough.mjs record --run-dir <run> [--listing-ref <stor-ref>]
cd <run>/project
npm run dacs:down
```

`dacs:down` stops both services and keeps their data. The record is described next.
If the `record` command rejects its arguments or run directory, an earlier `record.json` can remain;
do not treat it as the result of that attempt. Once the run directory passes validation, `record`
removes the earlier file before continuing, so a later failure leaves no `record.json`.

## The record

`record` observes the run as it is now and writes `<run>/record.json` (mode `0600`, replaced on a
rerun). It also prints the record as one JSON line. It makes no Demos, EVM or payment write, and
writes no readiness record or doctor report.

- **What it reads.** The public values in `project/.env`; the tarball hashes against the ones `init`
  saved; the EVM chain id again; and `/ready` of both services. With `--listing-ref` it also runs
  `npm run dacs:buy --silent -- --listing-ref <ref> --request-file ./request.json
  --max-service-amount 0.000001 --max-network-fee-eth 0.001` **without** a confirmation variable, so
  the buy only runs its doctor and, when that passes, prints its plan. That buy's doctor can leave a transport diagnostic in each
  role's outbox, and every `dacs:` script rebuilds the project's `dist/`. The raw output goes to
  `<run>/logs/buy.log`.
- **Fields.** `commit`, `packageVersion`, `tarballs` (name to sha256), `deployment`, `rails`,
  `network` (chain, USDC contract, facilitator host), `evmRpc` (host masked as `custom`), `demosRpc` (host, or
  `custom` with the chain identity), `authorities` (buyer, seller, steward), `payee`, `registry`
  (the two refs), `listingRef`, `readiness` (one entry per role), `steps` and `fundedRun`.
- **Step statuses.** Each entry of `steps` is `ran`, `blocked` or `unrun`, and an `unrun` entry
  carries its reason:

  | Step | Status |
  | --- | --- |
  | `init` | `ran` |
  | `registry` | `ran`, or `unrun` when the registry step saved no refs |
  | `readiness` | `ran`; `blocked` with the `/ready` reason codes; or `unrun` when a service was not observed |
  | `setup` | `ran` only when the buy exited 0 (it found the Listing); otherwise `unrun` |
  | `buy` | `ran` with `planOnly: true`; `blocked` with `exitCode` and `notPass` (each check's id, status and reason code); or `unrun` without `--listing-ref` |
  | `fundedPurchase` | always `unrun`, with the two reasons above |

  `fundedRun` reads `Funded run: UNRUN — <the two reasons>`.
- **Exit codes.** `record` exits 0 once it has written a record, even when steps are `blocked` or
  `unrun`. It exits 1 and writes no record when `init` has not run; when the chain is not Base
  Sepolia; when a tarball no longer matches; when `project/.env` is missing or holds a bad public
  value; when the EVM RPC cannot be reached or does not answer with a chain id; or when the buy does
  not finish or prints something other than a doctor report. A CLI argument error or run-directory
  validation error happens before the existing record is removed, so an earlier `record.json` may
  remain; after run-directory validation succeeds, any later failure leaves no record.
- **Before you share** `record.json`, read it. It holds public values. Both RPC hosts are masked as
  `custom`, except the Demos host when it is the default public one. **Never share** keys, phrases or tokens, `<run>/secrets`,
  `project/.env`, or `<run>/logs/*.log`, which hold raw output nobody has filtered.

## Troubleshooting

- **`doctor` exits 5 on a fresh project.** Exit 5 means at least one required check is blocked and
  none failed. The generated project calls this a blocked bootstrap, not a failure: it covers absent
  credentials, funding, signed registries, endpoints or reviewed adapters, and nothing is guessed or
  written. The code shows one specific cause: `dacs:up` treats a report whose only checks that did
  not pass are `local.data-directory`, `local.disk-space` or `local.sqlite` as expected, and creates
  the stores. This page does not say which checks block a given fresh project; read the check lines,
  and add `--explain` for next-step hints or `--json` for exact reason codes.
- **`/ready` answers 503 `readiness-latch-expired`.** The five-minute record ran out. Rerun the
  post-start doctor.
- **A Demos write is rejected because its reference block expired.** This has happened live. Rerun the
  same command and record what it prints. Whether a rerun completes the same write-once records is
  not verified.
- **Setup fails right after step 4.** Setup reads the rail registry through the Demos name index,
  which can trail a new write by a few blocks. If the setup plan run fails right after step 4, wait a
  minute and rerun it. This follows from the code and has not been seen on testnet.
- **Never use a fresh `dacs:buy` to recover** a purchase; use `--resume-job` with the same inputs.
- **`init` or `registry` refuses.** The message names the cause. To start over after `init` has run,
  create a new run directory with step 1; the wallets are new each time.
- **Funded testing.** `docs/live-e2e.md` §6 covers the funded test's own failures, including why a
  fresh run id can pay twice.
