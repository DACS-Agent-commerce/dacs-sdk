# @kynesyslabs/dacs-client

JavaScript ESM services for experimental host integrations and read-only diagnostics of retained DACS testnet operations using their original chain/RPC. This private package candidate is outside the repository's three-package release set. It is not a registry installation or a purchase-capable release. TypeScript, browser, public remote-seller transport and full agreement-capability transport integrations are outside this candidate's supported surface.

Use the SDK workspace after `npm ci` and `npm run build`, or install paired local artifacts into a JavaScript ESM application:

```sh
npm ci
npm run build
mkdir -p /tmp/dacs-artifacts
npm pack --ignore-scripts --pack-destination /tmp/dacs-artifacts
npm pack --workspace @kynesyslabs/dacs-client --pack-destination /tmp/dacs-artifacts
npm pack --workspace @kynesyslabs/dacs-node --pack-destination /tmp/dacs-artifacts
npm install /tmp/dacs-artifacts/kynesyslabs-dacs-0.1.0-alpha.0.tgz /tmp/dacs-artifacts/kynesyslabs-dacs-client-0.1.0-alpha.0.tgz /tmp/dacs-artifacts/kynesyslabs-dacs-node-0.1.0-alpha.0.tgz
```

All three artifacts must come from the same reviewed SDK revision. Release-set admission requires coordinated artifact, lifecycle, SBOM and publication checks; `private: true` prevents publication until that happens.

Every public entry point requires Node ^22.22.2 or ^24.15.0. The root does not load SQLite during import. `@kynesyslabs/dacs-client/wallet/durable-journal` separately exports the durable wallet journal, its format/version constants and the wallet-lane view. Source paths are private.

The client depends on `@kynesyslabs/dacs-node` (the exact same release), `@kynesyslabs/demosdk` (`^4.0.16`) and `@scure/bip39` (exact). The Node wallet session loads demosdk's websdk through an internal loading module that is not a package export and that the root import never reaches. It imports `@kynesyslabs/dacs-node/demos-loader`, which registers the SDK's package-scoped resolver for demosdk's one extensionless directory import, and then registers a reviewed load transform. The transform removes demosdk's own diagnostic output on the signing paths by replacing only these statements with an empty statement on the same line: GCRGeneration.js lines 173, 246, 249, 250 and demosclass.js lines 719, 1547 (demosdk 4.0.16), GCRGeneration.js lines 178, 302, 305, 306 and demosclass.js lines 738, 1767, 1773 (demosdk 4.0.17), GCRGeneration.js lines 178, 302, 305, 306 and demosclass.js lines 738, 1775, 1781 (demosdk 4.0.18), or GCRGeneration.js lines 254, 378, 381, 382 and demosclass.js lines 788, 2054, 2060 (demosdk 4.0.23). It first checks the source's SHA-256 against a reviewed table, then each listed line against its recorded text, then the output's SHA-256 against its recorded digest, and refuses any other source shape with `node_wallet_sdk_unreviewed`. Nothing assigns `console`, `process.stdout` or `process.stderr`. Host rule: build the composition before any other import of `@kynesyslabs/demosdk/websdk` in the process; a module imported earlier never passes through the transform, so loading refuses `node_wallet_sdk_preloaded`.

`createProtocolPurchases`, `createPurchaseService` and `createListingVerifier` require `admission: { binding, currentLocal }`: `binding` is the result of `bindTp1Profile` from `@kynesyslabs/dacs/wire` in the host composition, and `currentLocal` is a synchronous function returning the actor's current `{ endpoint, transportAuthority, connectionId }`. Construction throws `TypeError('admission_required')` without exactly those two members, `TypeError('admission_input_untrusted')` for a `profile`, `record`, `identityRecord` or `actionsAdmitted` option, and `OperationError('runtime_unsupported')` outside Node ^22.22.2 || ^24.15.0, all before any component is built. Every method except the passive readers returns a Promise. While the one hold constant is `held` it rejects `OperationError('profile_not_admitted')` before any binding read or effect; once admitted it rejects the same way, with the original error as `cause` (`tp1_authority_timeout` after 10,000 ms), unless the binding check passes and the hold and `currentLocal()` are unchanged, and only then runs the original once. The passive readers are the protocol's `assertBuyerAccess`, `supportsMode`, `readIssued`, `readIssuedPayment`, `observeReportedPayment`, `assertSellerReceiptReservation` (synchronous) and `readRetainedNativePaymentLane`, and the service's `status`, `portalOperation`, `portalEvidence`, `verifyDeal`, `planRunning` (synchronous) and `nativePaymentLaneRead`. While held, the service's readers return the diagnostic projection, chosen on each call. `actionsAdmitted` is a construction-time snapshot and never authorizes.

Portal entries require a nonempty primitive operation id (at most 256 characters) and handoff token (at most 1024). They authenticate the stored purchase capability before the host lookup or private reads: exact token bytes hashed as SHA-256 of `dacs-handoff-hash:` followed by the token, constant-time comparison with its lowercase hex hash, matching id/kind/owner, and a canonical `Date.toISOString()` lifetime later than both the business clock and internal wall clock. Both clocks must be valid nonnegative integer epoch milliseconds; the host may further refuse access.

Before constructing the service, migrate older databases with `ALTER TABLE operations ADD COLUMN handoff_expires_at TEXT` and provision explicit finite lifetimes. Missing columns produce `schema_migration_required`; null, malformed or past lifetimes grant no access, including links returned by status. Capability expiry is independent of approval `expires_at`.

Migrate evidence callers from `portalEvidence(operation)` to `portalEvidence(operationId, token)`. Evidence, status and public portal reads project approval expiry without writes. The protocol readback exception authenticates the same capability first. Purchase actions remain held.

Return fresh objects so projections cannot alter stored state. The host must derive each service call's `accountId` from its authenticated session, outside caller-controlled tool or request arguments. Public `status(accountId, operationId, token)` and `verifyDeal({ accountId, operationId, token, txHash? })` require the operation's unexpired handoff token as well as the owner id. Account and operation ids alone grant no access. Account lookups are checked against both the requested account and operation id before secondary reads. `portalOperation(operationId, token)` and `portalEvidence(operationId, token)` each authenticate through `ops.getByHandoff` on every call, before reading private coordinates. Both arguments must be nonempty strings (operation id at most 256 characters, token at most 1024); the returned operation must be a purchase with the requested id. Before consulting the host lookup, the package verifies the supplied token against the stored `operations.handoff_token_hash` with a constant-time SHA-256 comparison and checks the independent `handoff_expires_at` timestamp on every call. The hash is lowercase hex SHA-256 of `dacs-handoff-hash:` followed by the exact token (application wire contract pinned to `9d820e0:packages/dacs-client/test/helpers/purchase-integrity-operations.mjs:43` and the permanent capability vector). Store `handoff_expires_at` as canonical UTC ISO-8601 text produced by `Date.toISOString()` (for example, `2030-01-02T03:04:05.000Z`). SQLite `datetime()` text, epoch text, timezone offsets and local timestamps are refused. A missing, malformed or expired handoff lifetime refuses access. The optional `now()` clock must return a nonnegative safe integer in the JavaScript Date range, in epoch milliseconds; an invalid reading refuses access. Expiry uses the later of that reading and the internal wall clock, so a stale host clock cannot extend a capability. This expiry is separate from `expires_at`, which limits approval and may elapse while a diagnostic link remains valid. `portalEvidence` saves nothing: it reports an approval as `expired` once the `now()` clock or the wall clock has reached its expiry, without saving the transition. Approve, pay, cancel and the unpaid-purchase limits use the same two clocks, so an action is refused whenever a read reports `expired`. In the retained source service, `portalOperation` is also the entry for the portal's approval and payment actions, and saves that transition unless the host is stopped; the public diagnostic service only reports it. The returned owner must match the stored owner; the host lookup may further deny access. The retained protocol readback shortcut uses the same capability checks before its closed-wallet-access exception. Existing hosts must migrate `operations` to add the nullable `handoff_expires_at TEXT` column and provision explicit finite lifetimes before enabling portal reads; a null lifetime grants no access. Construction with the earlier schema throws `OperationError` with code `schema_migration_required` and identifies the missing column. Pass the id and token to evidence reads even when an earlier lookup returned an operation.

`openDurableWalletJournal({ path, mode, expectedJournalId?, lockTimeoutMs?, pollMs?, busyTimeoutMs?, maxRecords?, maxKeyBytes?, maxValueBytes?, maxTotalBytes? })` at `@kynesyslabs/dacs-client/wallet/durable-journal` takes `maxRecords` and `maxTotalBytes` per namespace (see below), and requires an absolute caller-owned path and explicit `mode: 'create'` (absent file) or `'open'` (existing intact journal). It synchronously returns `{ journalId, instance, path, get, put, entries, withWalletLock, appendUnderLock, withOwnedOrAcquiredLane, inspectLocks, releaseAbandonedLock, close }`; get/put/entries/withWalletLock/appendUnderLock/withOwnedOrAcquiredLane are async. Records must be exact JSON; writes and lane locks persist in SQLite, and close refuses active lane work. `appendUnderLock(laneKey, key, value)` adds a record that does not exist yet while the caller holds the lane, in one transaction, and never overwrites or writes a key another holder has locked; `withWalletLock(laneKey, work)` passes an opaque lane owner to `work(owner)`. `withOwnedOrAcquiredLane(laneKey, work, { owner } = {})` reuses that live owner even outside its async frame, or a lane held by the current frame, after checking that its lock row is still the caller's; without either it acquires the lane once. On every path it passes the lane's owner to `work(owner)`. A foreign, wrong-lane or released explicit owner refuses with `journal-fenced`; options that are not an object refuse with `journal-invalid`. The `eb/` dispatch history namespace and native records each have their own `maxRecords` and `maxTotalBytes` budget, so history cannot consume native capacity and a journal can hold twice either limit.

A lane lock left by a process that crashed is taken over only when its holder is proven dead. Opening the journal takes this process's lease in a private `holders` directory beside the journal file, an exclusive SQLite lock the kernel frees when the process ends; each lock row records its holder's lease, PID namespace, boot and start. Each process that opens a journal leaves one empty lease file there, and that file is the proof its process exited, so nothing here removes it. A holder is `exited`, and its lock is replaced when the next process acquires the lane, only on the same boot and PID namespace with a free lease and the original process no longer running. Age, a timeout or a PID alone never prove death, so a live or stalled holder keeps the lane `journal-busy`, as does any lock nothing proves gone (written by an earlier version, from another boot, with no identity, or with an unreadable lease). `inspectLocks()` reports each lock's `holder` class, and `releaseAbandonedLock({ key, instance, fence })` stays the explicit repair for those, after you have established that the holder is gone. Taking over a lock changes no record, so an issued lane still refuses a second send. Where more than one lock is needed the order is: the connection fence, then the wallet lane, then the per-address claim and refusal keys.
The factory and operations throw/reject `DurableWalletJournalError` with a `code`: `journal-invalid` for invalid arguments/records, `journal-exists`/`journal-absent` for mode/path mismatch, `journal-integrity` for damaged or unexpected journal identity, `journal-capacity` for limits, `journal-busy` for contention/active work, and `journal-closed` for use after close. Lock operations can also report `journal-reentrant`, `journal-fenced`, `journal-lock-live`, or `journal-lock-mismatch`; `appendUnderLock` reports `journal-key-exists` for an existing key and `journal-fenced` when the lane is not held or the key is locked by another holder; `withOwnedOrAcquiredLane` reports `journal-fenced` when a retained lane context no longer owns its lock row; opening reports `journal-lease-unavailable` when the process lease cannot be taken; other SQLite failures use `journal-error` and preserve their cause. Reopen with `expectedJournalId` to bind the retained journal; never recreate an absent journal to resume a lane.

The same subpath exports the wallet-lane view: the face the client's storage-anchor bridge gives the wallet as its `anchorJournal`.
`walletLane({ network, chainIdentity, address })` returns `JSON.stringify([network, chainIdentity, address])`, with the chain identity exactly as the wallet's transport binding carries it.
`walletLaneKey(lane)` returns `'sr2/wallet/' + lane`, and throws `TypeError('wallet_lane_invalid')` for an empty or non-string lane.
`createWalletLaneView({ journal })` returns `{ get(lane), put(lane, record), withWalletLock(lane, work) }` over your journal, and throws `TypeError('wallet_lane_journal_required')` unless it has those three methods.
`get` returns a copy of the lane record, or `undefined`. `put` stores a copy and reads it back, rejecting with `journal-error` when it differs.
It stores a `broadcast-accepted` stage as `sr2-readback-pending`, because only the client's own receipt readback releases the lane.
Call `put` inside `withWalletLock`, which holds the journal's lock on that key and passes its opaque owner to `work(owner)`.
Journal errors reach you unchanged. The native transfer lane is a separate lane.

Delta records also check parent continuity against the newest ancestor records for each path, or the publication baseline when no earlier record exists. A later record cannot legitimize a stale merge, deletion or restoration. Divergent parallel records require an explicit record of the merge resolution; that choice then constrains descendant records. This README is the one package file whose changes need no delta record; Git history shows who changed it.

## Public API

A plugin composes a purchase from the root names only. Each export's doc comment in `src/index.mjs` names what it returns and what it throws or rejects with; this section lists the factories' methods and the error contract.

The admission option: `admission: { binding, currentLocal }` is required by each factory below.
- Construction throws `TypeError('admission_required')` without exactly those two members, `TypeError('admission_input_untrusted')` for a `profile`, `record`, `identityRecord` or `actionsAdmitted` option, and `OperationError('runtime_unsupported')` below the Node floor.
- An active method returns a Promise. It rejects `OperationError('profile_not_admitted')` while the hold constant is `held`, or when the binding check fails, with the original error as `cause` (`tp1_authority_timeout` after 10,000 ms). Otherwise it resolves to, or rejects with, the original action's own result or error.
- A passive method keeps its original signature and is never wrapped. `actionsAdmitted` is a construction-time snapshot and never authorizes.

The stop option: `createProtocolPurchases` and `createPurchaseService` take an optional `stopped: () => boolean`, the host's synchronous stop check. A host fills it with a synchronous read, such as an `lstatSync` of its stop file. Without it, nothing changes.
- Construction throws `TypeError('stop_seam_invalid')` when `stopped` is not a synchronous function. A service given a `protocol` must carry the same function that protocol was built with, or construction throws `TypeError('stop_seam_mismatch')`; a service with no `protocol` may carry its own.
- The check is called on every use and never cached. While it returns `true`, an active method rejects `OperationError('writes_stopped')` before any authority read, and writes nothing except, on the service, the suspension of the protocol purchase its request authenticates for, whether or not work is queued, checked as that method checks it: by handoff token, or by account for `cancel` (see Seller answer classification). A request that does not authenticate records nothing. A check that throws rejects `stop_check_failed` with the error as `cause`; any other answer, including a promise, rejects `stop_check_invalid`. A promise's outcome is never read. `profile_not_admitted` comes first when both apply.
- The same check runs where a seller request is stored, before its pre-send check and at the wire signer, so nothing is signed with the session key and nothing is sent while the host is stopped. A stop that turns on in the middle of a call rejects it with the same `OperationError`, not a `SellerUnavailableError`, also when the wallet's effect boundary refuses a seller request while signing it or right before its first byte; a service method that rejects this way records the purchase's suspension as above. The agreement exchange catches seller-client errors, so `agreementSubmit` resolves with an indeterminate agreement note instead of rejecting.
- Passive methods never call it, except `portalOperation` and `verifyDeal`, which read it once when called. While the host is stopped both are readback only. `portalOperation` shows an elapsed approval as `expired` without saving it. `verifyDeal` saves no expiry, hash, settlement or `payment_uncertain` move and starts no seller or native payment work. Where its continuation would run, it records the purchase's suspension. It returns the stored row with `verification: { outcome: 'readback_only', reason }`, where `reason` is the stop's code. A purchase whose buyer access has closed keeps its source readback, which also carries `reason`.
- If that suspension cannot be saved, `verifyDeal` returns no readback: it rejects with the stop's own refusal, with the write's error as `details.suspensionWriteError`.
- It does not stop wallet effects or the wallet's own signatures; pass the same function to the wallet session. `createDeliveryDeadlineWatch` has no stop check: a stopped host must not start it, or must give it a delivery check that goes through the service.

The read-only option: `passiveOnly: true` on `createProtocolPurchases` and `createPurchaseService` builds a composition that can only read.
- `admission` is still required, and the construction checks run in this order: admission, the Node floor, `stopped`, then `passiveOnly`. Any value other than `true` or absent throws `TypeError('passive_only_invalid')` before the factory runs.
- The object carries the thirteen passive readers and the non-function members (`available`, `actionsAdmitted`, `nativePaymentReadbackAvailable` and, with a source capability, `chainReadback`). Every active name is absent, so calling one throws `TypeError` before any read or write.
- The service's readers return the diagnostic projection on every call, also after the hold lifts: `portalOperation` reports an elapsed approval as `expired` without saving it, `status` and `portalEvidence` give no approval link, and `verifyDeal` returns diagnostic readback without attaching a hash, settling or continuing the purchase.
- `stopped` stays optional, and no reader calls it in this mode. The protocol's source readers and `chainReadback` change no journal record and send only read-only node calls. Each node read takes and releases the source journal's `devnet/source-read/<bindingId>` lock, which advances the journal's lock fence and leaves no lock row.

The fee ceiling option: unless `passiveOnly` is set, `createProtocolPurchases` and `createPurchaseService` require `feeCeilingOs`, the host's per-write fee ceiling as a positive decimal OS amount string, and a `chain` with a `getTransactionFees()` function. There is no default. The root exports `PAID_WRITE_FEE_CEILING_OS`, the testnet value `"50000000000"` OS (50 DEM), for a host to pass explicitly.
- Construction throws `TypeError('fee_ceiling_required')` for a missing or malformed ceiling (`"0"`, a sign, a point, a leading zero, a number) or a `chain` with no `getTransactionFees`, after the `passiveOnly` check and before the factory runs. Construction never calls the fee reader.
- Each paid write is checked before anything is saved, moved, offered to a wallet or sent to a seller: the payment handoff and its re-offer (amount plus network fee), the cancel release transfer (1 DEM plus fee), and the buyer's Agreement CREATE (fee plus a 3 DEM storage reserve). A protocol start also refuses when the price plus fee, or the CREATE fee plus reserve, is over the ceiling. A debit equal to the ceiling passes. Over it, or with a fee that cannot be read, the action rejects `OperationError('write-fee-cap')` and the purchase stays as it was. Reading back an Agreement CREATE already issued, and a cancel whose nonce slot already holds another transaction of the wallet, are not checked: neither makes a new write.

The Agreement CREATE reserve and the anchor write record:
- The root exports `CREATE_STORAGE_RESERVE_OS`, `"3000000000"` OS (3 DEM): the storage reserve the buyer funds check at `prepare` holds for the buyer's Agreement CREATE, and the reserve the CREATE's fee ceiling check adds. It is the largest CREATE the native wallet allows (three 10 KiB chunks at 1 DEM each), not what the CREATE is charged.
- `prepare` for a protocol purchase reads the buyer wallet's account nonce after the funds check and saves an anchor write record in the purchase's state, in the same insert as the purchase, before anything is signed: `state.protocol.anchorWrite` is `{ kind: 'agreement-create', network, from, nonceFence, expectedNonce, jobId, reservedWriteId }`. A nonce read that fails or answers anything but a non-negative safe integer refuses `OperationError('anchor_nonce_unavailable')` and nothing is created. A replayed `prepare` returns the saved purchase without reading the nonce again.
- `readAnchorReservedWriteId(operation)` returns the record's `reservedWriteId`, 64 lowercase hex derived from the other six members. It is an intent id, not write evidence: `expectedNonce` is only the nonce read at `prepare` plus one, and the wallet plans the CREATE at the nonce it reads then. Match CREATE evidence to the record by `jobId`, `from` and `network`, never by `expectedNonce`. The read refuses `OperationError('anchor_write_unsaved')` for a missing operation, one that is not a protocol purchase or one with no record, and `OperationError('anchor_write_invalid')` (with `details.member`) when the record does not match the purchase's network, buyer wallet and job id or its id does not recompute. It reads and writes nothing else; nothing in the client releases, spends or changes the record.

### createProtocolPurchases

Active: `holdChainReadback`, `prepareTerms`, `assertSellerAdmission`, `identityRequest`, `agreementDelegation`, `sessionRenewal`, `sessionRenewalAccept`, `planRequest`, `runningPlan`, `planRunning`, `planFlightsRunning`, `signRequest`, `submitAgreement`, `recheckCommitment`, `nativePaymentClaimed`, `nativePaymentTermsCancelled`, `nativePaymentRefused`, `cancelNativePayment`, `nativePaymentFailed`, `nativePaymentSuperseded`, `nativeIntentsSupersededBy`, `withNativePaymentLane`, `readNativePaymentLane`, `checkDelivery`, `recheck`, `countersignRequest`, `countersign`

`prepareTerms` does not return `terms.jobId`; the create path adds it.

The Agreement starts in three wallet steps, each message saved before it is returned. `identityRequest` returns the seller session delegation message. `agreementDelegation` accepts its signature, has the session key ask the seller for its challenge, and returns the identity presentation message over the seller's nonce. Called without a signature, `agreementDelegation` accepts the delegation a session renewal saved, after the wire verifies it again. `planRequest` accepts the presentation and plans the Agreement. A purchase without a declared seller transport cannot ask for a challenge and is refused `seller_challenge_unavailable`. An unused challenge that expires before the presentation is accepted stops the start (`context_challenge_expired`).

Passive: `assertBuyerAccess`, `supportsMode`, `readIssued`, `readIssuedPayment`, `observeReportedPayment`, `assertSellerReceiptReservation`, `readRetainedNativePaymentLane`

A composition with `dacsProtocol.nativeAgreementPayment` takes two more options, and has no default for either:

- `receiptFeeCeilings`: exactly `{ payFeeCeilingOs, anchorFeeCeilingOs }`, each canonical decimal OS text (`0` allowed, at most 78 digits). Anything else throws `OperationError('receipt_fee_ceilings_invalid')`.
- `buyerMandateCapOs`: the buyer's approved mandate cap as canonical decimal OS text. Anything else throws `OperationError('buyer_mandate_cap_invalid')`. The ceilings are checked first.

The seller's signed ordinary commit answer carries `sellerReceipt: { agreementHash, reservedMaximumOs }`. The protocol keeps it with the verified commitment only when it has exactly those members, is canonical and names this purchase's Agreement. `assertSellerReceiptReservation(operation)` reads only the operation it is given. It throws `OperationError('seller_receipt_reservation_insufficient')` unless the kept receipt's `reservedMaximumOs` equals the approved price plus both fee ceilings and is no more than the mandate cap. A composition without native payment always refuses. `prepareHandoff` checks it before the payment nonce is read and again on the saved row before the coordinates are written, and `readNativePaymentLane` checks it before the one-time wallet guard is issued. A refused handoff stays `approved` and offers no payload; a refused lane read leaves the guard unissued.

### createPurchaseService

Active: `prepare`, `issueApprovalChallenge`, `approve`, `prepareHandoff`, `nativePaymentLane`, `reportWalletResult`, `cancel`, `agreementIdentity`, `agreementDelegation`, `sessionRenewal`, `sessionRenewalAccept`, `agreementPlan`, `agreementSubmit`, `completionRequest`, `completionCountersign`, `protocolRecheck`

Passive: `status`, `portalOperation`, `portalEvidence`, `verifyDeal`, `planRunning` (synchronous), `nativePaymentLaneRead`

The native payment lane readback: `nativePaymentLaneRead({ operationId, token, key })` reads back the wallet lane of a native purchase whose one-time wallet guard `nativePaymentLane` already issued. The protocol's `readRetainedNativePaymentLane(operation, key)` is the same read without the token.
- It works while purchase actions are held and while the host is stopped. It never calls `stopped`, rechecks the commitment or Agreement on chain, asks the seller, signs, takes a lock or saves anything.
- It needs an unexpired handoff token and buyer access. It reads back only a lane whose guard was issued once after an approved handoff; before that it rejects `native_payment_lane_held`.
- It re-reads the stored approval, coordinates, handoff and guard events, retained Agreement receipt and seller commitment, and requires them to still match. Any mismatch, missing record or change while the lane is read rejects `native_payment_lane_unverified`; nothing is refreshed. The service also requires its configured chain to be the purchase's declared binding and reads the RPC's chain identity once (`network_identity_mismatch`).
- It resolves `{ record: { readback: true, retained: { stage, hash, nonce } } }`: the retained Agreement CREATE's lane, with no top-level `stage`, `hash` or `nonce`, so a wallet guard reader does not take it as a second send. `nonce` is the CREATE's own nonce, not the payment's. A lane that no longer holds that CREATE rejects `wallet_fenced`; another lane key rejects `wallet_lane_mismatch`. It says nothing about the chain's current state or the payment.

Active: `verify`

Passive: none

### createPublicSellerClient

`createPublicSellerClient({ admission, publicEndpoint, authentication, timeoutMs, commitOnSignature })` sends signed POSTs to one public HTTPS seller origin. It accepts no other option: no fetch function, resolver, certificate authority, connector or transmit callback. `authentication` is the purchase's wire authentication. `timeoutMs`, when given, is an integer from 1000 through 300000, and `commitOnSignature` is a boolean; any other value throws `TypeError`. The client keeps no request records.

Active: `propose`, `agreementState`, `commit`, `submitPayment`, `bundleRequest`, `countersign`, `confirmBuyerCopy`, and `commitOnSignature` when that option is true

Passive: `origin` (a string)

### createPurchaseEvidenceRecorder

`import { createPurchaseEvidenceRecorder } from '@kynesyslabs/dacs-client/purchase/evidence-recorder'`. It records the transaction hash, nonce and state a wallet reported for a delivery, and reads back what the journal retains for that delivery's CREATE. It can cause nothing: it signs, sends, continues and asks a wallet for nothing.

`createPurchaseEvidenceRecorder({ admission, journal })` takes the open durable wallet journal from `./wallet/durable-journal` and opens no store of its own. Construction applies the admission shape and Node floor checks of the factories above and throws `TypeError('journal_required')` unless `journal` has `get`, `entries`, `withWalletLock` and `appendUnderLock`. No call runs the binding check, the hold or the stop check, so every method works while held, stopped and with a failing binding. Recording never lifts a suspension.

- `recordWalletResult({ deliveryId, hash, nonce, state })` resolves `{ status, count }`. `hash` is 64 lowercase hex, `nonce` a non-negative safe integer, `state` one of `submitted`, `rejected` or `unknown`. The report is not rejected with an error when it is malformed: it resolves `{ status: 'invalid_report' }` and writes nothing, so check `status`. Otherwise `status` is `recorded`, `repeat` for a report identical to one kept (no slot used), or `evidence_limit` for a ninth distinct report (history unchanged). Journal errors, such as a busy lane, reject unchanged.
- `resultHistory(deliveryId)` resolves the kept reports in the order they were accepted, each frozen with `verified: false`. A report is a pointer the wallet gave, never proof that a transfer happened or settled; check the chain before relying on it.
- `openRetainedCreateJournal({ deliveryId })` resolves a frozen `{ deliveryId, records }` holding only the retained signed CREATEs that name `deliveryId`, whatever their journal key. The caller authenticates the delivery first. It refuses any other input, such as a `laneKey`, with `reader_input_invalid` before reading. It selects by shape, without verifying signatures or checking the chain, reads the whole journal once and has no write, lock or resume member.

### Other exports

- The capability constructors `createDemDeliveryContext`, `createNativeDemDeliveryCapability`, `createNativePaymentEvidenceConsumer`, `createSourceDemoSellerTransport` and `createDevnetNativeCommitmentCapability` return a frozen opaque capability and throw `TypeError` for a missing or malformed input. All but `createNativePaymentEvidenceConsumer` take an `authority` that is a `TEST-` label (a `TEST-RUN-` label for the commitment capability) or an authority token, and, with a token, the `binding` it was admitted for (see "Authority tokens and labels" below).
- `createDemosNetworkBinder` is the shared read-only chain-identity binder. Its observations are independent of each other; only `exclusive: true`, which the transport's own fenced binders set, refuses an overlapping call with `binding_busy`. `createAuthorityReader({authority, identityRecord, claim, listings, purchases, participantImplementations})` is the production `Tp1AuthorityReader` for `bindTp1Profile`. It needs no completed binding, reads the chain through `authority.authorityRpc` and its local evidence on every call, and takes no fence, lock or signer. A counterparty is answered only when a registered Listing (discovery) or the saved purchase row (a job) relates it to the scope and exactly one current enrollment in `participantImplementations.entriesFor(claim)` names it; anything else answers no participants, which the wire refuses as `tp1_participant_profile_mismatch`. A connection on another chain answers no decision (`tp1_connection_unverified`); a transport failure rejects with its original error.
- `purchaseNext`, `protocolView` and `PURCHASE_STATUS_HELP` read the hold constant on every call or read: historical held text while held, the full text once admitted.
- `OFFLINE_AGREEMENT_MODE` and `DEVNET_NATIVE_COMMITMENT_MARKER` are constants. `isOfflineWalletAgreement` returns a boolean; `deriveStorageAddress` returns text and throws `TypeError` for a non-text owner.
- Every other export states its own contract in its doc comment. Failures are the exported error classes (`OperationError`, `NotWiredError`, `OutboundError`, the seller and wallet errors), which keep their cause. No export hands out a fixture identity, a simulation header or an unqualified chain reader.

## Public Demos chain reader

`@kynesyslabs/dacs-client/substrate/demos` exports only `createDemosPublicChainReader({rpcUrl, network, pinnedIdentity, timeoutMs, fetchImpl})`. It accepts only `network: 'testnet'` with the 64-hex chain identity pinned for testnet, and otherwise throws `OperationError` `invalid_configuration`. It holds no key and cannot sign or send.

The returned frozen object has nine reads: `readStorageProgram`, `getAddressBalance`, `getTransactionFees`, `networkIdentity`, `getAddressNonce`, `observePurchaseTransfer`, `observeTransfer`, `getTransaction` and `findTransferAtNonce`. Later reads rely on a successful check, but a read whose answer is marked simulated throws the same error instead of returning it and the next read checks again; a failed check is not reused. ## Node wallet session

`@kynesyslabs/dacs-client/node-wallet` exports `createNodeTransportOwner`, `createNodeObserver`, `createNodeAuthorityCapability`, `createRpcStampSource`, `createHeldTransportFacade`, the TP-1 token functions `admitTp1Authority`, `tp1AuthorityLabel`, `authorityLabelOf` and `isTp1AuthorityToken`, `releaseAbandonedJournalLocks({journal, stateOwnership})`, `passContext` (see the effect gate below), and the asynchronous `createNodeWalletSession`, `composeNodeWalletSession`, `openKeystoreWalletSession` (see the keystore entry below) and `createNodeSellerComposition`. `createNodeAuthorityCapability({owner, claim})` returns the read-only capability the production authority reader uses, `{authorityRpc(body, {signal}), claim(), context(), connectionGeneration()}`, with no sign or send. `authorityRpc` sends only `getBlockByNumber` and `getNetworkInfo` (`readonly_only` otherwise) over the owner's transport, takes no fence, journal lock or signer, limits a reply to 4 MiB before decoding and 1024 entries per array or object after (`authority_list_too_large`), runs at most four reads at once, and gives the reads queued behind them one 10 s deadline (`tp1_authority_timeout`, cause kept). `composeNodeWalletSession` builds the buyer's session in stages from an unopened owner: the capability, the production authority reader, `bindTp1Profile`, the effect boundary, then the session. It also needs `identityRecord`, `listings`, `purchases`, `participantImplementations`, `stopped` and `feeCeilingOs`, makes `admission` itself and returns the session's members plus `binding` and `effectBoundary`; a failed stage leaves no composition. `createNodeObserver({owner, clock})` returns the read-only observer `{observe({signal}), readNodeInfo(message, {signal}), provenance()}`: its expected identity and block-one fallback come only from the SDK-approved TP-1 record, it acquires no connection fence and no journal lock and signs nothing, every node reply is limited to 4 MiB before decoding, each call has one 10 s deadline (`tp1_authority_timeout`) and a caller's abort starts no further read; `readNodeInfo` admits only `getNetworkInfo` and `getNetworkParameters`. Construct the owner on a canonical HTTPS root and bind the SDK-approved TP-1 record to `owner.currentLocal()`. Pass `{admission: {binding, currentLocal: owner.currentLocal}, owner, journal, key, approve, clock, stopped, feeCeilingOs}` (the last two are described below); `key` is UTF-8 mnemonic bytes and is consumed and zero-filled on every outcome. Build the composition before any other import of demosdk.

The returned `wallet.request` is held (`profile_not_admitted`); purchase runtime is Node `^22.22.2 || ^24.15.0`. `getPublicAccount`, `getWriteProfile`, `isLocked` and `lock` remain passive. The synchronous `walletFactory({anchorJournal})` selects a journal for the same wallet identity; it exposes the same held request API. `close()` locks that wallet and closes its transport; the host closes its owner and journal. All SDK posts use the bounded native transport in process. A native broadcast that may have reached the node is never repeated after broadcast intent; restart reads back the original evidence. A broadcast refused at its last check before its request sends nothing; readback answers it `failed` (resolved), and the same signed bytes may go out once through a new lease. Durable pre-confirmation recovery and the owning effect-boundary passes that supply the gate below are prerequisites for lifting the hold.

`openKeystoreWalletSession` is the buyer's keystore entry. The SDK reads the recovery phrase, so the host never holds it. It takes `keystorePath` (an absolute path to the wallet plugin's keystore), `passphrase`, `expectedAddress` (the Demos address the host bound) and the options of `composeNodeWalletSession` except `key`, and returns that composition. It reads only the plugin's version-1 format: UTF-8 JSON `{version: 1, kdf: "scrypt", kdfparams: {N, r: 8, p: 1, salt}, cipher: "aes-256-gcm", iv, tag, ciphertext}` with standard padded base64 members (32-byte salt, 12-byte IV, 16-byte tag), N a power of two from 2^14 to 2^20, the key `scrypt(passphrase NFKC, salt, 32)`, and AES-256-GCM with no additional data. The optional `address` and `onboarding` members are not trusted. It refuses, in this order and before the file is opened:
- a `TypeError` naming the option, for a `key` option, any pass-rule option (`passRequired`, `jobContextRequired`, `requirePass`), a path that is not absolute, an empty passphrase, an address that is not a Demos address, a missing `stopped` or `approve`, a bad `feeCeilingOs` or a journal without its methods;
- `runtime_unsupported` below the purchase floor;
- `writes_stopped`, `stop_check_failed` or `stop_check_invalid` from one call of `stopped()`, which must answer a boolean synchronously.

Then it reads the file once and refuses:
- `keystore_unreadable` for a file that is absent, a link, not a regular file, readable or writable by group or others, over 65,536 bytes, or not that format;
- `keystore_unlock_failed` for a wrong passphrase or changed bytes;
- `invalid_mnemonic` for a phrase that is not 12, 15, 18, 21 or 24 lowercase words;
- a composition stage's own error;
- `keystore_address_mismatch`, after closing the composition, when the wallet is not `expectedAddress`.

Messages never echo the path, the passphrase or the decipher's error. It writes, caches and logs nothing, never creates or rewrites a keystore, and zero-fills every phrase copy it makes. Its session needs a current effect pass for every transaction signature and every `confirmTx` and `broadcastTx` body (`effect_pass_required`, before anything is signed or sent). A plain `passContext()` pass is enough, and no option turns the rule off.

A keystore buyer pays only for content it approved beforehand, in three steps. Outside any effect pass, `preparePaidWrite` (below) gives the exact content, and the host shows `content` and gets the user's approval of those bytes. Then `authorizePaidWrite(prepared, content)`, on the composition (for its default wallet) and on each wallet view, resolves an opaque one-use permit. Inside its effect pass, the host sends the same request once, on the view that prepared it, with `wallet.request(request, {paidApproval: permit})`. The wallet's approval step compares its complete approval request with the approved `content` and spends the permit. Before the inner transaction signature, the session compares the content Demos finalized with `signedContent`, and the pass's fee ceiling with the approved `feeCeilingOs`; a higher or a lower ceiling is refused too. Any difference fails `paid_approval_mismatch` with nothing signed or sent. The host's `approve` callback is not asked for this write; it still answers the keystore session's other approvals, such as a `sign` request.

`authorizePaidWrite` resolves only for the view's own handle and field-for-field equal content. It rejects `paid_approval_mismatch` for another view's or another session's handle and for any other content, a params value or digest included; `paid_approval_used` once the handle has authorized a permit; and `profile_not_admitted` while held. A `sendTransaction` request answers one of these before anything is signed, authenticated or sent: `paid_approval_required` with no permit or one this session did not mint; `paid_approval_used` for a permit already entered; `paid_approval_mismatch` on another view, or for a request that differs anywhere from the prepared one; `invalid_params` for a second argument other than exactly `{paidApproval}`, or a request that is not bounded plain JSON. Such a refusal leaves the permit usable once for its unchanged request. A request that passes these checks spends the permit whatever happens next, even when a read fails before anything is signed. A permit lives only in its session's memory. When an outcome is unknown, read back the wallet's retained transfer or anchor before preparing another write; a new write, or a new session after a restart, needs a new preview and approval. The preview refuses a keystore CREATE request holding a string that is not in Unicode NFC form, even though the wallet's own CREATE hashing normalizes such a string.

`preparePaidWrite(request, {feeCeilingOs})`, on the composition (for its default wallet) and on each wallet view (for its journal), is the read-only preview of one native send or Agreement CREATE `sendTransaction` request, made before any effect pass. It resolves `{content, signedContent, prepared}`: `content` is the complete approval request `{method, address, purpose, content}`, whose content adds `nonceSource`, `observedNonce` and the intended pass `feeCeilingOs` to what the wallet's approval callback shows; `signedContent` is the `transaction.content` demosdk 4.0.17 will sign; `prepared` is an opaque handle. Both projections are deeply frozen copies, with no observation time or observation provenance. It reads the source binding, the nonce, the fees and the denomination through the transport's keyless reads, and never signs, authenticates, confirms, broadcasts, executes or writes a journal record. It rejects `profile_not_admitted` while held; `invalid_params` for options other than a positive decimal OS `feeCeilingOs`, a request that is not bounded plain JSON (undefined, symbols, functions, accessors, holes, non-plain containers, cycles, non-NFC strings), another method, a malformed transaction, or a missing or non-positive safe-integer timestamp; `fee_ceiling_above_session`; `locked`; `wrong_wallet` for another wallet's transaction; `nonce_lane_order` inside an effect pass; `outcome_unknown` while the wallet's native lane holds a transfer that is not `observed` or `failed`, or, for a CREATE, the view's anchor lane holds one that is not `broadcast-accepted`; `transport_closed`, `upstream_unavailable`, `stale_plan`, `network_binding_unavailable` or `network_binding_required` for its reads; and the anchor planner's refusals of a CREATE whose envelope, signed scope or derived address differs.

Before the SDK's inner transaction signature, the session checks synchronously that the signed message is the transaction hash (or, once the node's `signatureDomain` fork is active, `demos-tx:v1:<decimal chain id>:` followed by it), that the hash is the SHA-256 of `JSON.stringify(content)`, and that the SDK's finalized content (amount, fees, edits, and the denomination the node reported at approval) is exactly what was approved, returned as two canonical OS amount strings; otherwise the request fails `payload_mismatch` and nothing is signed. The returned `internalCauseOf(envelope)` gives the host the error a failed request was closed over; its `cause` chain holds the original failure, which the public envelope never carries. `confirm_rejected` means only a validated `valid:false` answer; a malformed, non-200 or unavailable confirmation, or a `valid:true` answer this session cannot match to the approval, is `upstream_unavailable`, and nothing is broadcast after either.

A general `sign` request (an identity presentation, a delegation, an Agreement or its anchor authorization) passes through the effect boundary like a transaction signature. It signs only after the boundary's final stop check, under the approved TP-1 record, and a stop, a re-hold or a reconnect that arrives first refuses the request and releases no signature. The journal records each such signature before it is released. The header signature that a storage-write recovery makes for its confirmation and its resend is checked the same way under the recovery's own fence, and it is never stored.

The native transport checks the signature of every transaction it confirms or broadcasts against what the configured node's `getNetworkInfo` says it covers: the bare hash while the `signatureDomain` fork is inactive, `demos-tx:v1:<chain id>:<hash>` once it is active, and no other form. A `getNetworkInfo` answer that cannot be read, or that does not say whether the fork is active (or gives no chain id for an active one), refuses the request with `signature_domain_unreadable` or `signature_domain_malformed` and nothing reaches the node. The answer is kept for one connection only: an active fork is kept, an inactive answer is reused for a minute, and a failed read is tried again on the next request. A request that holds no signature lease reads nothing.

A storage CREATE reads the node (the chain identity, and for a recovery the absence of the transaction and the account nonce) before it asks the node to confirm. Between the confirmation and the broadcast, or the recovery's single resend, the node receives no write and no other confirmation. Only local checks run, plus at most one getNetworkInfo read for the signature-domain check, made only when the kept answer is older than a minute. That read never changes the kept reference block. The confirmation's `reference_block` is kept on the write's lane and intent rows as `storageWriteReferenceBlock`, is replaced only when a recovery reconfirms the exact same bytes, and is handed back as `referenceBlock` on the broadcast result and on a pending `readback`. A confirmation that carries no reference block gives `referenceBlock: null`; it is never filled from a block height. A native transfer keeps and reports none.

The seller composition takes the same options plus required `publications: {settlementPublication, deliveryPublication, demoArtifactPublication}` and `approveConfirmedWrite` (a function in policy mode, an explicit `null` in manual mode; any other value throws `TypeError`). Its session and facade share one transport and journal. It returns the session members plus `transport` (the held facade), `observer` (built from its own owner) and `paymentEvidenceAdapter`. A confirmation by another sender, or of a Listing CREATE, passes without the policy; every other seller confirmation calls it once, and `false` or a throw refuses `approval_required` (a thrown error is kept as `cause`) with nothing broadcast. The policy is asked after the node's acknowledgement is recorded, so the node is not asked to confirm those bytes again; a later confirmation of them in the same operation asks the policy again on the recorded answer. Buyer sessions install no confirmed-write policy. Each publication policy's `authority` is a `TEST-` / `TEST-RUN-` label or an authority token admitted for the composition's own binding, which the composition passes to the transport; the policy declares the token's label.

Every composition has one effect gate and a host contract for it. The gate runs at the transaction-hash signature inside `NodeDemos.sign` and at every `confirmTx` or `broadcastTx` body sent through the owner's fetch, the transport's recovery included; RPC-authentication signatures and read bodies pass through. After the SDK's own preparation awaits, one gate pass awaits `qualify` (seller only, when installed), then the pass's `refreshAuthority`, then its `finalStop`, each within the pass's remaining deadline. A result after the deadline refuses. Then, in the same synchronous run, it checks the hold, `currentLocal()` against the binding's local, the connection generation `qualify` returned against the current one, the pass's fence lease, each of its `synchronousChecks` (one that returns a promise refuses), and at the signature the finalized content and debit, with only the finalized fees (`feeDebitOs`, not the amount) compared to the pass's own `feeCeilingOs` from `effectPass` (equal passes, above it refuses `write-fee-cap`). This per-pass fee cap is separate from the session's `feeCeilingOs`, which caps the amount plus fees. Only then does it invoke the signature or the real fetch. A refusal invokes neither, keeps the failing step's own code (`effect_gate_refused` when its error has none) with its error as `cause`, and at transmission reports `not_dispatched`. Steps refuse by throwing; the gate holds no durable state and acquires no fence.

- `createNodeSellerComposition({..., stateOwnership})`: `stateOwnership` is `{directory, held()}`, the host's proof that it holds the state lock for the directory containing `journal`; without it construction throws `state_ownership_required`. Before returning, the composition removes the lock rows of dead holders from `journal` (never a row of a live handle or holder, never by elapsed time, and it changes no record) and retires every signer reservation that has no signed bytes. `releaseAbandonedJournalLocks({journal, stateOwnership})` is that first half alone, for the host's other client journals in the same directory: it resolves `{released: [lock keys]}` and throws `state_ownership_required` when `held()` is not true or the journal's real path is outside `directory`.
- `createNodeSellerComposition({..., paymentEvidenceApproval})`: the kit's approval ledger for payment-evidence CREATEs, `{prepare, open, reopen, confirm, settle}`; construction throws `invalid_params` unless all five are functions. `approveAhead` and `approveSendAhead` also need the ledger's synchronous `revocationGeneration()`, a count of the releases it has started, and refuse `approval_required` without it; construction still checks only the five. The composition returns `paymentEvidenceAdapter` with the six members listed below. `signCreate(input, {signal})` resolves `{signedTransaction, txHash, nonce}` and sends nothing. `input` is exactly `{logicalAddress, artifact, writer, artifactKind, jobId, receiptContentHash}`; any other member throws `signer_input_invalid`.
  - `signCreate` runs inside the caller's effect pass and keeps one live write per signer: it throws `signer_lane_busy` while the signer has another reservation or an issued native write on the transport's own lane, and `locked` once the session's wallet is locked.
  - `approveAhead(input, {signal})` takes the approval before the caller's effect pass, so the operator's decision is not limited by the pass's deadline. It runs outside every effect pass. It first checks that the wallet is unlocked, that purchase actions are admitted and that `stopped()` answers `false`, and checks the same again right before it asks `prepare`. It reserves the signer, reads the fees from the pinned node, fixes the timestamp, stores the approval request, asks `prepare` and binds the answer. It resolves `{approval}`, a hold for that exact request, or `{answer}`, the stored bytes when the reservation already holds them for this input. It holds no lock, queue, fence or pass while the ledger or the operator decides. The signer stays reserved until the hold is used or released, and another write of the signer is refused `signer_lane_busy` at once.
  - `signCreate(input, {signal, approval})` runs in the caller's pass and uses the hold once. Before the inner signature it checks that the hold is this wallet's (another wallet's hold is refused and left unused), then the input, the reservation, the open authorization, the chain's next nonce and the fee reads against the approved ones. Then the gate's synchronous run checks that the hold is still current: no stop, and no release started on the ledger since the hold was made. It signs the bytes that were approved. A refusal is `approval_required` for a hold or authorization that is no longer current and `approval_mismatch` for another input or a moved nonce or fee. A refusal before the bytes are stored retires the reservation and releases the authorization; a grant the operator gave alone is ended first, so the same request is asked of the operator again. As for the other members, `signal` is optional.
  - `approval.release()` ends an unused hold the same way, and never rejects: it resolves `{released: true}`, or `{released: false}` when the reservation could not be retired, with the cause from `internalCauseOf`; recovery at the next construction retires it. Call it in `finally`. A hold neither used nor released keeps the signer reserved until the composition is built again.
  - `approveSendAhead({signedTransaction, txHash}, {signal})` makes the stored bytes' authorization current before the caller's pass, so the operator's decision on a replacement is not limited by the pass's deadline either. It runs the authorization steps of `broadcast` below with the same checks before it starts and right before it asks, and asks for a replacement only when the exact request has none open. It resolves `{approval}`, a send hold; its `release()` resolves `{released: true}` and changes nothing, since the authorization stays with the stored bytes. `broadcast(retained, {signal, approval})` then asks for no new authorization: one that is no longer the reservation's or no longer open refuses `approval_required` and nothing is sent. The gate's last synchronous run before `broadcastTx` checks the hold again, so a stop or a release started on the ledger during the send's awaits also refuses `approval_required` with nothing sent.
  - It reads the fee inputs only after the node's chain identity matches the pinned one. It stores its approval request before calling `prepare`, binds the returned id before signing, and stores the signed bytes before returning. The SDK's finalized content, fee and edits are compared with the approved CREATE before the inner signature.
  - The same evidence's stored bytes come back for the same input with no new signature. A changed input throws `signer_lane_busy`: signed bytes are never retired, and only an execution of them frees the signer.
  - Any other failure before the signed bytes are stored (a refused approval, a failed read, a gate refusal, a locked wallet at the signature, a signer failure, an abort) releases the authorization and frees the nonce. A signature that arrives after an abort is dropped.
  - An abort while `prepare` has not settled, or a failed store the read-back cannot decide, keeps the reservation and throws `signer_reservation_uncertain`. A later call for that evidence returns the bytes if the store did commit; otherwise it throws the same until the next construction's recovery retires the reservation.
  - `open(requestText)` resolves null or the one open `{ledgerId, requestText}`, and `settle({ledgerId, requestText}, outcome, reason)` is idempotent for the same outcome and must refuse a settlement whose outcome differs from the one already recorded: the replay check settles a released-or-spent authorization `released` again, and relies on that refusal to tell a spent one.
  - `broadcast({signedTransaction, txHash}, {signal})` runs in an effect pass, signs nothing and dispatches the held bytes at most once per call, with no retry. It refuses `retained_transaction_invalid` unless the reservation holds exactly these bytes. It reopens the stored authorization by id. If the ledger no longer holds it open, it first reads the chain for the held bytes the way `readTransactionState` does: an execution ends the reservation and refuses `transaction_already_executed`, and any answer other than the chain saying it has not seen the hash refuses `approval_required`; both send nothing, so an authorization that an execution spent is never replaced by a second one, also after a restart. Even when the chain says it has not seen the hash, an id the ledger shows spent is not replaced (`approval_required`, nothing sent), because that answer may be stale. A manual authorization has no id, so every broadcast reads the chain for the held bytes first. Otherwise it uses the exact request's open authorization or asks for a new one, and the reservation stores that id before anything is sent. It then checks that the node serves the pinned chain (a refusal sends nothing) and sends `confirmTx` with the exact projection. A confirmation that is not a valid answer for those bytes is `outcome_unknown` and sends nothing more; a valid refusal is `confirm_rejected`. `confirm(binding, validity)` runs on every call, and `false` or a throw is `approval_required` with the authorization still held. The send runs under the signer's reservation lock, which a native write holds while it issues and a readback holds to end the reservation. Under that lock the reservation must still hold these bytes, else `retained_transaction_invalid` with nothing sent. Any failure after `broadcastTx` starts is `outcome_unknown`. Both transmissions carry fresh authentication headers from the wallet's stamp source and pass the effect gate.
  - `readAccountNonce({signal})` resolves the account nonce. `readTransactionState({signedTransaction, txHash, nonce}, {signal})` resolves `{state: 'applied'}` only when the node's chain identity is authenticated and the executed transaction is in a block that lists the hash, with the same signature and complete content as the held bytes, and the node serves the storage program the CREATE made (its address, data, metadata, program name and owner, and creation provenance that names this CREATE in both members or in neither). The seller journal passes the bytes and nonce it keeps, so a CREATE whose reservation has ended still reads back; given only `{txHash}`, it uses the bytes the reservation holds for that hash. It then ends the reservation that holds them and settles its authorization `spent` by id; when the ledger refuses the spend and no longer holds the authorization open (an operator released it), the reservation ends without a settlement. Everything else, including a failed execution and any failed or aborted read, is `{state: 'pending'}`, with the cause available from `internalCauseOf`. It never answers `absent`, so a kept CREATE is never superseded by this adapter. Each node reply is limited to 4 MiB and 10 seconds.
- `createNodeWalletSession({..., stopped, feeCeilingOs})` and `createNodeSellerComposition`: the host's stop check `stopped()` and its fee ceiling `feeCeilingOs` (a positive decimal OS amount) are required, with no defaults; a missing or malformed one throws `TypeError` before anything is opened. The effect boundary accepts a `stopped()` that answers a promise, but the payment-evidence adapter's `approveAhead` and `approveSendAhead` read it synchronously: a stop check that answers anything but a boolean synchronously makes them refuse `stop_check_invalid` (a throw: `stop_check_failed`) before anything is reserved or asked. The session's `feeCeilingOs` caps the whole debit of each paid write, the amount plus every fee, not the fees alone: the signature lease and the confirmation check the amount, and the broadcast checks the amount plus the confirmed fees (`write-fee-cap`, nothing sent). The session builds the client's effect boundary from them over the admitted binding, the journal and the owner's connection fence, gives it to its native transport (which requires one), and returns it as `effectBoundary` next to the held `transport` facade. On the buyer composition a pass made without a `context` is a plain pass; the seller composition takes only a pass with a job context and refuses a pass without one `effect_pass_invalid`, before anything is signed or sent. A job context, which the host that owns the job makes with `passContext({operationClass, operationId, currentAuthorization})` (exported by this subpath), carries the job's class and its current-authorization check; that check runs with the boundary's dispatch checks, before the broadcast's lane and intent records are written (a job withdrawn by then is withheld and leaves the wallet's lane free), at the transport's last check, and again in the gate's synchronous run right before the request. Any other `context` is refused `effect_pass_invalid`.
- `createNodeSellerComposition({..., qualify})`: `qualify({phase, signal})` is absent or a function that resolves the connection generation (its `connectionId`) it observed; anything else, and any `qualify` on the buyer composition, throws `invalid_params`.
- `effectPass({fence, deadline, refreshAuthority, finalStop, synchronousChecks, feeCeilingOs})` returns a frozen handle registered to this composition, and authorizes nothing by itself. It throws `effect_pass_invalid` unless `fence` is a live lease from this composition's own transport owner, `refreshAuthority` and `finalStop` are functions that take `{phase, signal}`, `synchronousChecks` is an array of functions that take `{phase}`, `deadline` is a number on the composition's `clock` between now and 10,000 ms ahead, and `feeCeilingOs` is a canonical positive OS string.
- `runInEffectPass(handle, work)` runs `work` with `handle` as the current pass and returns its result; a `work` that is not a function throws `invalid_params`. While `work` runs, a fence acquisition on the exported transport owner shares the pass's fence and is granted at once (its release frees nothing), so the transport's own steps do not wait on the fence the pass holds. The seller composition refuses `effect_pass_required` when no pass is current, and any composition refuses `effect_pass_invalid` for a handle it did not make (a copy, another composition's), or whose lease is no longer live. The buyer composition runs without a pass, except the session `openKeystoreWalletSession` composes, which refuses `effect_pass_required` like the seller's but accepts a plain pass; no request field, environment value or per-call option supplies or disables a step.
- `withheldReopen` has two members, for the trusted composition only: the held `transport` facade, the wallet and a wallet relay carry neither. It is the explicit request that sends a retained native transaction whose whole dispatch history shows no possible transmission, once, under the job owner's pass context; it also reaches one whose lane and intent rows were left at `broadcast-started`, which a new lease refuses. `register({operationId, lane, hash, operationClass, currentAuthorization})` returns a one-use capability for the retained native transaction `hash` that operation signed on wallet lane `lane` (`reopen_scope_invalid` for a malformed scope); `operationClass` and `currentAuthorization` are the job owner's private pass context (as for a job pass), run again at the broadcast's last check. `reopen({capability, signRpc})` runs the lease, confirmation and broadcast of that transaction's own retained bytes and takes no transaction; it restores the retained `confirm-acknowledged` answer when the last confirmation was acknowledged, and otherwise confirms again. The capability is consumed by its first pass, whether that refuses or transmits (`reopen_capability_invalid` for an unknown or used one). A transaction whose history shows an acknowledged, unknown or unpaired dispatch, or any recovery, held or observed record, or whose lane or intent row holds a broadcast answer, stays readback-only for good. So does a transaction that was never sent but that a readback later marked failed because another transfer used its nonce. `reopen` also refuses when the history is missing, conflicting or incomplete; when the transaction has an intent row, or a lane row that names it, and the two rows do not both name it, or they conflict, one at `broadcast-started` and the other finished as withheld (a readback finishes a lane left at `broadcast-started` next to a withheld intent row as withheld too); and when the lane row names another unfinished transfer. Each of these refusals is `outcome_unknown` with the cause and sends nothing. When the transaction has no intent row and the lane row is absent or holds another, finished transfer, as when a broadcast was withheld before its rows were written, the history alone decides, and one that shows no possible transmission is sent.
- The TP-1 token: `admitTp1Authority({binding, currentLocal})` resolves a frozen token after the wire's binding check under 10 s; `tp1AuthorityLabel(binding)` returns `TP1-` plus 32 hex digits of `binding.recordDigest`; `authorityLabelOf(value)` returns a token's label or a canonical label unchanged and throws `authority_unbound` otherwise; `isTp1AuthorityToken(value)` is a boolean. A token authorizes nothing by itself and a label string is not a token.

#### Authority tokens and labels

A token is the object `admitTp1Authority` returns; the label is its serialized form, `TP1-` plus 32 hex digits. The capability constructors above that take an `authority` (all but `createNativePaymentEvidenceConsumer`) and the native transport's settlement, delivery and demo publication policies (the transport's `authorityBinding` option) take either a fixture label or a token. A token is accepted only for the binding object it was admitted for, never by comparing labels, because two connections over the same record have equal labels. What the constructor stores and declares, and what signed metadata carries, is the label string. A plain `TP1-` string is refused `authority_unbound`, as is a token of another binding. A token is refused `profile_not_admitted` while purchase actions are held; fixture labels need no admission. `isDemDeliveryContextAuthority` and the portal provider's transport check accept label strings only and grant nothing. A CREATE retained under one label is recovered only by a declaration with the same label: a `TEST-` create is not recovered under a `TP1-` declaration, nor the reverse.

A host that forwards a wallet relay's sends passes the relay's own last check as a third argument: `facade.rpc(body, headers, { currentAuthorization })`. `currentAuthorization` is a synchronous function. It returns `true` while the relay's authority is current and throws its own error when it is not, for example when a capability has expired, a handoff has closed or the wallet binding has changed.

The transport runs the check as the last step before each node request of that call, after every wait the call makes (the lease, the wallet-lane lock, the binding reads and the history writes). It sends only when the check returned `true`. A throw refuses with the thrown error, and any other answer, including a promise, refuses with `context_authorization_refused`. A refusal sends nothing and leaves the client's usual withheld record for that stage. A broadcast that is refused leaves its lane free for a later call.

The option is refused with `relay_authorization_invalid` (a `TypeError`) unless it is a plain object with exactly one member, the function `currentAuthorization`. It is refused with `relay_authorization_nested` inside another pass, a job pass or another relayed call, whose own check it never replaces. Both refusals come before the hold check and before any transport call.

What the option does not cover:
- It is opt-in. A call without it runs no relay check, so a relay host must pass it on every forwarded `rpc`.
- It does not run for preparation reads, or for a confirmation the retained record already answers, because neither sends a transaction.
- It does not apply to `walletBinding`, `binding`, `recoverStorageWrite` or `cancelNativeTransfer`. `walletBinding` sends no transaction, and a lease it grants is useless until a relayed `rpc` send, which runs the check.
- It can run twice for one broadcast: once before the lane and intent records are written and once right before the request. Keep it cheap and free of side effects.

### Wallet nonce lane

The seller composition's `transport.withWalletNonceLock({owner, network, chainIdentity}, work)` runs `work` while it holds the wallet's native lane. That is the lock row every native write of that wallet takes on the same client journal file, a buyer composition's writes included. A seller artifact anchor takes it from its nonce read to its broadcast, so two writes of one wallet never take the same nonce.

- The scope is exactly those three keys: the wallet's `0x` address, `transport.pins.network` and `transport.pins.chainIdentity`. Anything else is refused `invalid_params`.
- It is an active member. While the purchase hold is held it refuses `profile_not_admitted`, and it reads the connection authority once per call.
- Inside `work`, the transport's readback, CREATE recovery and broadcast for that wallet continue in the held lane. A lease that names a native transfer, that transfer's confirmation and `cancelNativeTransfer` refuse `journal-reentrant`.
- It waits at most the journal's lock timeout (2 s by default) and then refuses `journal-busy`, before `work` runs. Nothing queues or retries.
- It is taken before any effect pass and refuses `nonce_lane_order` inside one. A readback, recovery or leased broadcast that holds the connection fence and then meets a held lane refuses `journal-busy` after the same wait.
- The lane is released when `work` settles, whatever its outcome. The call rejects with `work`'s own error, or with `journal-fenced` when the lock row was removed while `work` ran. Steps inside `work` that need the lane after that removal refuse `journal-fenced` before they send.
- It reads nothing from the node, writes no journal record and signs nothing. `transport.close()` waits for it.
- It does not serialize writers of the same wallet that use another journal file.

The entry also re-exports the boolean capability checks `isDevnetAgreementTransport`, `isDevnetSettlementTransport` and `isDevnetDemoTransport`, and the declarations `DEVNET_AGREEMENT_PROFILE`, `DEVNET_AGREEMENT_KIND`, `DEVNET_AGREEMENT_SOURCE`, `DEVNET_SETTLEMENT_KIND`, `DEVNET_SETTLEMENT_POLICY`, `DEVNET_DELIVERY_KIND`, `DEVNET_DELIVERY_POLICY`, `DEVNET_DEMO_ARTIFACT_KIND`, `DEVNET_DEMO_ARTIFACT_POLICY` and `DEVNET_DEMO_ARTIFACT_TYPES`. No raw transport constructor is exported.

## Seller transport composition

`createSourceDemoSellerTransport({authority, sessionSignerFor, sessionPolicyFor, endpointProofFor, effectBoundary})` takes three functions of the purchase: the session signer `{claim, sign}`, the expiry policy `{expiresAt}` and the endpoint proof that the wire's `verifyEndpointProof` returned (verified with the buyer's own commitment receipt reader). It also takes the `effectBoundary` of the Node composition. Each request is signed through the boundary: after its final stop check, and only under the approved TP-1 record. The same boundary checks the request again right before its first byte, and a request it refuses is not sent. A request that goes out leaves nothing in the wallet journal, since it is signed again whenever it is sent; a signature that a stop, a re-hold or a reconnect refuses after it was made is kept there, unreleased. Its `authority` is a `TEST-` label or an authority token admitted for `binding` (also passed as an option). Prepare declares this transport in the terms only together with `nativeAgreementPayment` and `nativePaymentEvidence`; without all three it rejects with `OperationError('seller_agent_unavailable')` before anything is signed or saved, because no seller request could be authenticated.

The seller client sends only to a public HTTPS origin: `https://` and an authority, with no credentials, path prefix, query or fragment (the wire's `isPublicEndpoint`), and not a private or loopback address. Any other endpoint, and any option the client does not take, throws before anything is signed or sent. There is no plain-HTTP or loopback transport. Every call goes through one pinned connector: it resolves the host, admits only public addresses, verifies TLS for the host name, reads at most 512 KiB of body and 16 KiB of headers, never follows a redirect (a 3xx is unavailable with cause `redirect`) and reports whether any request byte was written. Purchase actions, and `createPublicSellerClient`, are still refused while the release gate holds them.
Requests, delegation bytes and received response bytes go through `@kynesyslabs/dacs/wire` under the purchase's kept TP-1 profile. The client saves the delegation payload before it returns the wallet message, stores the wallet signature as canonical base64url, and refuses a purchase prepared under the old transport declaration with `seller_transport_changed`. The seller request timeout also bounds the wire's authority reads and the session signer: a seller call that has not finished signing by then sends nothing and fails with cause `timeout`, and a wallet message or delegation check that is still waiting for the authority fails with `seller_authority_timeout`.
Payment and bundle requests (the wire's continuing routes) and the two ordinary read routes (`agreements/state`, `bundles/buyer-copy`) of a committed purchase are signed with the job's finalized commitment, its two-party Agreement and the signed Listing, as canonical bytes rebuilt from the purchase row. The commitment's anchored tuple is kept with its SHA-256 when the commitment verifies. A verified row with no usable kept bytes keeps them once from a fresh authenticated readback that matches the stored summary, and otherwise nothing is signed (`commitment_unverified`). The proof's receipt reader authenticates the commitment at every signing, so these requests sign under a `ready: false` proof and after the Listing's window ends, with no continuation capability. Challenge, context, proposals and commitment requests carry no commitment evidence, and a read before commitment keeps the wire's live Listing checks. `bundles/buyer-copy` has no such read before commitment, so the wire refuses it without evidence.

### Seller session keys

`createSellerSessionKeys()` returns `{start, stop, stopAll, state, signerFor}`, a registry of random ed25519 session keys for the seller transport. Pass `signerFor` as `sessionSignerFor` to `createSourceDemoSellerTransport`, and call `start(operationId)` before the purchase's identity request. `start` returns only the key's `claim`.

The keys live in process memory and nowhere else. No key is written to a file, a database, a journal, an event or a log, and none is derived from the wallet's recovery phrase. Memory hygiene is partial: the registry zero-fills its own seed on `stop`, but Node keeps a copy inside each private-key object it builds to sign, which the registry cannot clear.

After a restart the registry is empty, and a purchase whose saved delegation names a key from before the restart answers `session_gone_reapprove` before anything is signed, sent or recorded. Passive readers and chain readback keep working. To continue, the buyer approves a new key for the same authority:

1. `start(operationId)` makes a key in the new process.
2. `sessionRenewal` returns `{operation, delegation: {payload, message}}`. The payload keeps the buyer, seller, Listing pin, job, profile and `expiresAt` of the saved delegation, and changes only `sessionPublicKey` and `notBefore`. The buyer's wallet signs `message`.
3. `sessionRenewalAccept` takes that signature, verifies it against the purchase's own scope, and replaces the saved delegation and its wallet message. It never accepts an unsigned or unverified delegation.
4. The host then continues through the existing entries, passing no `delegationSignature` to `agreementDelegation`; `agreementPlan` takes none.

`sessionRenewal` answers `session_live` while the saved key is still held, `session_not_started` before `start`, `seller_session_ended` after the seller session ended, `invalid_state` when the purchase has no saved delegation, `seller_delegation_expiring` when the delegation of an unpaid purchase (no transfer can have been sent) is inside its safety margin of its expiry, `seller_delegation_expiring_payment_unresolved` inside that margin when a transfer may already have been sent but is not verified (`payment_handoff`, `broadcast_reported`, `payment_uncertain`): the buyer must not pay again or prepare a new purchase, but verify or recover the payment first, and `seller_delegation_expired` when the delegation of a paid (`settled_verified`) purchase has expired or its expiry is unknown; a paid purchase renews right up to that expiry, since the renewal is how the seller hears of the payment after a restart. `sessionRenewalAccept` answers `session_gone_reapprove` when there is no pending renewal or its key is no longer the live key, and `seller_delegation_expired` (the wire's `peer_delegation_expired` kept as its `cause`) when the delegation of a paid purchase expired before the renewal was accepted; nothing is saved. While it rebuilds the wallet message after the verification, `sessionRenewalAccept` can also answer `seller_authority_timeout` or `tp1_local_binding_changed`; nothing is saved and the pending renewal stays. `signerFor` answers `session_gone_reapprove` or `session_not_started` for a purchase with or without a saved delegation. `start` throws `TypeError('session_operation_invalid')` for an id that is not a non-empty string.

### Seller answer classification

Each answer is verified on its exact received bytes, then classified by its HTTP status and `error` code, the route, and the request's provenance. The transport builds the record `{status, signed: true, body}` only after verification; an answer that fails verification is `unknown`. A `result` or `progress` answer is returned. Every other class throws: `definite` and `failed-bootstrap` as `SellerRefusedError` (`code` is the seller's code), the rest as `SellerUnavailableError` (`answerCode` is the seller's code). Both carry `answerClass`. In a protocol purchase, each seller route stores its exact request bytes under the purchase revision (`state.protocol.sellerRequests`) before the first send; the two read routes store nothing. A call with a stored attempt retries an unknown dispatch at most twice, 5 seconds apart, using the same bytes and fresh wire nonces. Unrecorded reads send once. One absolute deadline (15 seconds by default; context 240–300 seconds) includes storage, authority reads, signing and transport; an exhausted budget signs and sends nothing further. Unknown outcomes remain unknown, and a later explicit call reuses stored bytes. Failures before dispatch clear only their own attempt; swallowed failures retain their bounded class and cause. `createPublicSellerClient` keeps no request records: each call signs and sends once, nothing is stored or retried, and nothing about an unknown outcome survives a restart.

A definite failed context bootstrap ends the purchase as `agreement_rejected`, stage `bootstrap-failed`.
The saved `bootstrapEnd` retains the seller's code, HTTP status and recorded cause.
An unused challenge that expires before presentation acceptance ends the same way.
Only an explicit new purchase obtains a new job, challenge and wallet delegation; earlier attempts may have done seller work.
A verified `party_vet_non_pass` instead ends at `agreement-rejected`, keeping its `counterparty` or `permanent` error class, with no fresh Start offered.
Neither end retries or returns another wallet message. Unknown outcomes stay pending; an accepted presentation can be retried after challenge expiry.
The plan step's context scope carries the `generatedAt` of the challenge scope saved in step 2, because the seller compares the two. A retry or restart sends the same scope.
An approved Agreement time that differs from it is refused with `agreement_time_mismatch` before any context read.

A verified `seller_stopped` answer (class `suspended`) durably records `state.protocol.sellerSuspension: {id, cause, path, at}`. So do a re-hold and a host stop (`writes_stopped`, `stop_check_failed`, `stop_check_invalid` or `stop_check_timeout` as `cause`), whether or not work is queued, when a seller request that stores its bytes sees them as it starts, before its send or at the wire signer, when the effect boundary raises them while that request is signed or right before its first byte, or when `verifyDeal` or its continuation sees them. A re-hold raised there still rejects as an unsent `SellerUnavailableError`. A host stop that refuses a service method also records it, for the purchase the request authenticates for. On the two read routes, only queued work records one. A purchase keeps its first suspension and its `id`: a later stop or re-hold records nothing. When a method rejects with a re-hold or host stop refusal whose suspension write failed, the refusal keeps its own `cause` and carries the write's error as `details.suspensionWriteError`. Retries and queued continuations stop, the outcome stays unknown and a dispatched payment is never marked failed. The record and the stored request bytes survive restart and every later save, and re-admission alone resumes nothing. `verifyDeal` keeps its readback and bookkeeping but does not continue a suspended purchase. The protocol view exposes the suspension. To resume, make a new explicit `protocolRecheck({operationId, token, resumeSuspensionId})` request with the suspension's `id`: it checks admission and buyer access again, then clears only the suspension it names, so an older request cannot clear a newer stop. Do not pay again.

## Factory integration

Supply application inputs through host, including a synchronous operations-store factory; the package ships one, with the approval challenges and a local account (see Shipped host adapters). On a fresh database, apply the schema, construct the purchase store first, then prepare all statements (reads as well as writes). Existing databases need application-owned migrations preserving the schema constraints. Use the same connection for operation and coordinate writes.

```js
import { DatabaseSync } from 'node:sqlite';
import {
  PURCHASE_STATE_SCHEMA, createSqlitePurchaseStore, createCoordinateStore,
  createProtocolPurchases, createPurchaseService, createDeliveryDeadlineWatch,
  PAID_WRITE_FEE_CEILING_OS,
} from '@kynesyslabs/dacs-client';

const db = new DatabaseSync(':memory:');
db.exec(PURCHASE_STATE_SCHEMA);
const store = createSqlitePurchaseStore();
const ops = host.createOperations(db);
const coordinates = createCoordinateStore({ db });
const protocol = createProtocolPurchases({
  db, ops, coordinates, store, dacsProtocol: host.dacsProtocol,
  buyerAccess: host.buyerAccess, admission: host.admission,
  chain: host.chain, feeCeilingOs: PAID_WRITE_FEE_CEILING_OS,
});
const purchases = createPurchaseService({
  db, ops, coordinates, store, protocol, config: host.config, admission: host.admission,
  accounts: host.accounts, verifier: host.verifier, chain: host.chain,
  challenges: host.challenges, purposes: { APPROVE_PURCHASE: 'purchase-approval' },
  feeCeilingOs: PAID_WRITE_FEE_CEILING_OS,
});
const watch = createDeliveryDeadlineWatch({ db, ops, coordinates, store, enabled: true });

store.transaction(db, () => {
  ops.transition(host.operation.id, host.operation.status, host.operation.status, {
    state: { hostNote: 'local bookkeeping' }, event: 'host_bookkeeping', data: {},
  });
  coordinates.save(host.coordinate);
});
const diagnostic = purchases.status(host.accountId, host.operation.id, host.token);
```

The synchronous `store.transaction` commits both writes or rolls both back on an error. Nested synchronous calls use savepoints. Keep transaction control, database configuration and schema changes outside callbacks; asynchronous callbacks and results refuse. Call diagnostics outside the transaction. This example records host bookkeeping and grants no purchase or settlement authority.

### Shipped host adapters

`createPurchaseOperations`, `createPurchaseChallenges` and `createLocalPurchaseAccount` build `ops`, `challenges` and `accounts` on the same database and store as the factories. They write only inside the store's transaction.

```js
const ops = createPurchaseOperations({
  db, store, handoffSecret: host.handoffSecret, handoffTtlMs: host.handoffTtlMs,
});
const accounts = createLocalPurchaseAccount({ db, store, wallet: host.walletAddress });
const challenges = createPurchaseChallenges({
  db, store, origin: host.origin, purpose: 'approve-purchase', ttlMs: 300_000,

// Pass ops, accounts and challenges to both factories, and
// purposes: { APPROVE_PURCHASE: 'approve-purchase' } to createPurchaseService.
```

- `handoffSecret` (at least 32 characters) and `handoffTtlMs` are required and have no default. A purchase's handoff token is an HMAC of its id under the secret; it is never stored, and the handoff lifetime is never extended. Keep the secret across restarts: with another secret, earlier purchases can no longer be read through their tokens. `isPurchaseOperationId` is true exactly for the ids its `createIdempotent` mints.
- A host that writes its own `ops` keeps what the shipped one does: one operation per account, key and request (`idempotency_conflict` for another request), `job_id` and `handoff_expires_at` written in the same insert, the saved status compared in `transition`, and only a hash of the handoff token stored.
- The account id is derived from the wallet: `local:` followed by the normalized address, one `accounts` row per wallet. A saved row for that wallet that does not match refuses `local_account_mismatch`.
- `issue` needs an account id (`challenge_account_required`). Every challenge is signed under the one `origin` the host passes at construction; an `origin` given to `issue` refuses `challenge_origin_not_accepted`. `purchaseApprovalChallengeText` rebuilds the signed text from the fields `issue` returns and that origin.
- `verifyAndConsume` reads, checks and consumes a challenge in one store transaction, so a challenge is consumed at most once, and only for a signature by its own wallet.

### Database admission

Use main and TEMP only; detach all other schemas before a package transaction. Admission is checked again on every transaction, before the callback. Persistent files require WAL with synchronous FULL or EXTRA, or a rollback journal with EXTRA. Configure foreign keys and a bounded busy timeout outside the transaction.

- `purchase_store_persistent_attachment`: a file-backed attachment is present.
- `purchase_store_unsupported_attachment`: another attachment, including an in-memory attachment, is present.
- `purchase_store_unsupported_journal_mode`: main has an unsupported journal mode, including OFF or a persistent MEMORY journal.
- `purchase_store_unsupported_synchronous`: a persistent main database lacks the required durability setting; SQLite defaults are insufficient.
- `purchase_store_unsupported_temp_journal_mode`: TEMP has an unsupported journal mode, including OFF.

### Chain reader

For legacy and native purchases alike, provide `network`, `pinnedIdentity`, `networkIdentity` and `observePassiveTransfer`. Network identity resolves the configured identity and mode. The passive reader observes the saved hash without journal reconciliation. Missing or noncallable passive readers produce unavailable readback. It returns one object with these primitive fields:

| Field | Presence | Contract |
| --- | --- | --- |
| `status` | always | `included`, `pending`, `not-found`, `failed`, `invalid` or `unavailable` |
| `reason` | optional | text of at most 240 characters |
| `txHash` | included | the requested hash: 64 hex characters, with an optional `0x` prefix |
| `payer` | included | readable Demos address of at most 66 characters |
| `payee` | included | readable Demos address of at most 66 characters |
| `amountOs` | included | text matching `OS_INTEGER`: canonical decimal integer in OS units, at most 78 digits |

| `includedAt` | optional | for included observations, integer epoch milliseconds from 0 to 8640000000000000 |
| `sourceDisposition` | optional | exactly `included` or `failed` |

### Operations

`ops` is synchronous, returns fresh hydrated operations, preserves original errors and uses the same database connection. Diagnostics use only `get`, `getByHandoff` and `history`. The additional `transition` method is used only by `watch.observe`; it must compare the saved status and atomically update state and append its event, refusing a stale status. The package ships one (see Shipped host adapters).

### Diagnostics

The public diagnostics are `status`, `portalOperation`, `portalEvidence` and `verifyDeal`. They authenticate the operation's handoff capability on every call, project elapsed approval windows without saving a transition, and return historical state or non-authoritative observations. Readback uses only the saved transaction hash. It cannot authorize payment, settlement or delivery.

### Protocol

The protocol pass-through methods are exactly `assertBuyerAccess`, `supportsMode`, `readIssued`, `readIssuedPayment`, `observeReportedPayment`, `assertSellerReceiptReservation` and `readRetainedNativePaymentLane`. The seller receipt reservation check is synchronous and refuses a missing, unequal or over-cap seller receipt with seller_receipt_reservation_insufficient. Methods outside this list refuse with `profile_not_admitted` before host effects. No caller option lifts the action hold.

### Writers

The writer list is exactly `watch.observe`: host bookkeeping that cannot establish settlement. It can record a host's not-present delivery observation against an already verified payment; the saved status stays unchanged.

Run `npm test --workspace @kynesyslabs/dacs-client` after building the SDK.
