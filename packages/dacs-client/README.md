# @kynesyslabs/dacs-client

JavaScript ESM services for experimental host integrations and read-only diagnostics of retained DACS testnet operations using their original chain/RPC. This private package candidate is outside the repository's three-package release set. It is not a registry installation or a purchase-capable release. TypeScript, browser, public remote-seller transport and full agreement-capability transport integrations are outside this candidate's supported surface.

Use the SDK workspace after `npm ci` and `npm run build`, or install paired local artifacts into a JavaScript ESM application:

```sh
npm ci
npm run build
mkdir -p /tmp/dacs-artifacts
npm pack --ignore-scripts --pack-destination /tmp/dacs-artifacts
npm pack --workspace @kynesyslabs/dacs-client --pack-destination /tmp/dacs-artifacts
npm pack --workspace @kynesyslabs/dacs-node --pack-destination /tmp/dacs-artifacts
npm install /tmp/dacs-artifacts/kynesyslabs-dacs-0.1.0-alpha.0.tgz /tmp/dacs-artifacts/kynesyslabs-dacs-client-0.1.0-alpha.0.tgz /tmp/dacs-artifacts/kynesyslabs-dacs-node-0.1.0-alpha.0.tgz
```

All three artifacts must come from the same reviewed SDK revision. Release-set admission requires coordinated artifact, lifecycle, SBOM and publication checks; `private: true` prevents publication until that happens.

Every public entry point requires Node ^22.22.2 or ^24.15.0. The root does not load SQLite during import. `@kynesyslabs/dacs-client/wallet/durable-journal` separately exports the durable wallet journal and its format/version constants. Source paths are private.

The client depends on `@kynesyslabs/dacs-node` (the exact same release), `@kynesyslabs/demosdk` (`^4.0.16`) and `@scure/bip39` (exact). The Node wallet session loads demosdk's websdk through an internal loading module that is not a package export and that the root import never reaches. It imports `@kynesyslabs/dacs-node/demos-loader`, which registers the SDK's package-scoped resolver for demosdk's one extensionless directory import, and then registers a reviewed load transform. The transform removes demosdk's own diagnostic output on the signing paths by replacing only these statements with an empty statement on the same line: GCRGeneration.js lines 173, 246, 249, 250 and demosclass.js lines 719, 1547 (demosdk 4.0.16), GCRGeneration.js lines 178, 302, 305, 306 and demosclass.js lines 738, 1767, 1773 (demosdk 4.0.17), or GCRGeneration.js lines 178, 302, 305, 306 and demosclass.js lines 738, 1775, 1781 (demosdk 4.0.18). It first checks the source's SHA-256 against a reviewed table, then each listed line against its recorded text, then the output's SHA-256 against its recorded digest, and refuses any other source shape with `node_wallet_sdk_unreviewed`. Nothing assigns `console`, `process.stdout` or `process.stderr`. Host rule: build the composition before any other import of `@kynesyslabs/demosdk/websdk` in the process; a module imported earlier never passes through the transform, so loading refuses `node_wallet_sdk_preloaded`.

`createProtocolPurchases`, `createPurchaseService` and `createListingVerifier` require `admission: { binding, currentLocal }`: `binding` is the result of `bindTp1Profile` from `@kynesyslabs/dacs/wire` in the host composition, and `currentLocal` is a synchronous function returning the actor's current `{ endpoint, transportAuthority, connectionId }`. Construction throws `TypeError('admission_required')` without exactly those two members, `TypeError('admission_input_untrusted')` for a `profile`, `record`, `identityRecord` or `actionsAdmitted` option, and `OperationError('runtime_unsupported')` outside Node ^22.22.2 || ^24.15.0, all before any component is built. Every method except the passive readers returns a Promise. While the one hold constant is `held` it rejects `OperationError('profile_not_admitted')` before any binding read or effect; once admitted it rejects the same way, with the original error as `cause` (`tp1_authority_timeout` after 10,000 ms), unless the binding check passes and the hold and `currentLocal()` are unchanged, and only then runs the original once. The passive readers are the protocol's `assertBuyerAccess`, `supportsMode`, `readIssued`, `readIssuedPayment` and `observeReportedPayment`, and the service's `status`, `portalOperation`, `portalEvidence`, `verifyDeal` and `planRunning` (synchronous). While held, the service's readers return the diagnostic projection, chosen on each call. `actionsAdmitted` is a construction-time snapshot and never authorizes.

Portal entries require a nonempty primitive operation id (at most 256 characters) and handoff token (at most 1024). They authenticate the stored purchase capability before the host lookup or private reads: exact token bytes hashed as SHA-256 of `dacs-handoff-hash:` followed by the token, constant-time comparison with its lowercase hex hash, matching id/kind/owner, and a canonical `Date.toISOString()` lifetime later than both the business clock and internal wall clock. Both clocks must be valid nonnegative integer epoch milliseconds; the host may further refuse access.

Before constructing the service, migrate older databases with `ALTER TABLE operations ADD COLUMN handoff_expires_at TEXT` and provision explicit finite lifetimes. Missing columns produce `schema_migration_required`; null, malformed or past lifetimes grant no access, including links returned by status. Capability expiry is independent of approval `expires_at`.

Migrate evidence callers from `portalEvidence(operation)` to `portalEvidence(operationId, token)`. Evidence, status and public portal reads project approval expiry without writes. The protocol readback exception authenticates the same capability first. Purchase actions remain held.

Return fresh objects so projections cannot alter stored state. The host must derive each service call's `accountId` from its authenticated session, outside caller-controlled tool or request arguments. Public `status(accountId, operationId, token)` and `verifyDeal({ accountId, operationId, token, txHash? })` require the operation's unexpired handoff token as well as the owner id. Account and operation ids alone grant no access. Account lookups are checked against both the requested account and operation id before secondary reads. `portalOperation(operationId, token)` and `portalEvidence(operationId, token)` each authenticate through `ops.getByHandoff` on every call, before reading private coordinates. Both arguments must be nonempty strings (operation id at most 256 characters, token at most 1024); the returned operation must be a purchase with the requested id. Before consulting the host lookup, the package verifies the supplied token against the stored `operations.handoff_token_hash` with a constant-time SHA-256 comparison and checks the independent `handoff_expires_at` timestamp on every call. The hash is lowercase hex SHA-256 of `dacs-handoff-hash:` followed by the exact token (application wire contract pinned to `9d820e0:packages/dacs-client/test/helpers/purchase-integrity-operations.mjs:43` and the permanent capability vector). Store `handoff_expires_at` as canonical UTC ISO-8601 text produced by `Date.toISOString()` (for example, `2030-01-02T03:04:05.000Z`). SQLite `datetime()` text, epoch text, timezone offsets and local timestamps are refused. A missing, malformed or expired handoff lifetime refuses access. The optional `now()` clock must return a nonnegative safe integer in the JavaScript Date range, in epoch milliseconds; an invalid reading refuses access. Expiry uses the later of that reading and the internal wall clock, so a stale host clock cannot extend a capability. This expiry is separate from `expires_at`, which limits approval and may elapse while a diagnostic link remains valid. `portalEvidence` saves nothing: it reports an approval as `expired` once the `now()` clock or the wall clock has reached its expiry, without saving the transition. Approve, pay, cancel and the unpaid-purchase limits use the same two clocks, so an action is refused whenever a read reports `expired`. In the retained source service, `portalOperation` is also the entry for the portal's approval and payment actions, and saves that transition; the public diagnostic service only reports it. The returned owner must match the stored owner; the host lookup may further deny access. The retained protocol readback shortcut uses the same capability checks before its closed-wallet-access exception. Existing hosts must migrate `operations` to add the nullable `handoff_expires_at TEXT` column and provision explicit finite lifetimes before enabling portal reads; a null lifetime grants no access. Construction with the earlier schema throws `OperationError` with code `schema_migration_required` and identifies the missing column. Pass the id and token to evidence reads even when an earlier lookup returned an operation.

`openDurableWalletJournal({ path, mode, expectedJournalId?, lockTimeoutMs?, pollMs?, busyTimeoutMs?, maxRecords?, maxKeyBytes?, maxValueBytes?, maxTotalBytes? })` at `@kynesyslabs/dacs-client/wallet/durable-journal` requires an absolute caller-owned path and explicit `mode: 'create'` (absent file) or `'open'` (existing intact journal). It synchronously returns `{ journalId, instance, path, get, put, entries, withWalletLock, appendUnderLock, withOwnedOrAcquiredLane, inspectLocks, releaseAbandonedLock, close }`; get/put/entries/withWalletLock/appendUnderLock/withOwnedOrAcquiredLane are async. Records must be exact JSON; writes and lane locks persist in SQLite, and close refuses active lane work. `appendUnderLock(laneKey, key, value)` adds a record that does not exist yet while the caller holds the lane, in one transaction, and never overwrites or writes a key another holder has locked; `withOwnedOrAcquiredLane(laneKey, work)` reuses a lane the caller already holds, after checking that its lock row is still the caller's, or acquires it once.

A lane lock left by a process that crashed is taken over only when its holder is proven dead. Opening the journal takes this process's lease in a private `holders` directory beside the journal file, an exclusive SQLite lock the kernel frees when the process ends; each lock row records its holder's lease, PID namespace, boot and start. Each process that opens a journal leaves one empty lease file there, and that file is the proof its process exited, so nothing here removes it. A holder is `exited`, and its lock is replaced when the next process acquires the lane, only on the same boot and PID namespace with a free lease and the original process no longer running. Age, a timeout or a PID alone never prove death, so a live or stalled holder keeps the lane `journal-busy`, as does any lock nothing proves gone (written by an earlier version, from another boot, with no identity, or with an unreadable lease). `inspectLocks()` reports each lock's `holder` class, and `releaseAbandonedLock({ key, instance, fence })` stays the explicit repair for those, after you have established that the holder is gone. Taking over a lock changes no record, so an issued lane still refuses a second send. Where more than one lock is needed the order is: the connection fence, then the wallet lane, then the per-address claim and refusal keys.
The factory and operations throw/reject `DurableWalletJournalError` with a `code`: `journal-invalid` for invalid arguments/records, `journal-exists`/`journal-absent` for mode/path mismatch, `journal-integrity` for damaged or unexpected journal identity, `journal-capacity` for limits, `journal-busy` for contention/active work, and `journal-closed` for use after close. Lock operations can also report `journal-reentrant`, `journal-fenced`, `journal-lock-live`, or `journal-lock-mismatch`; `appendUnderLock` reports `journal-key-exists` for an existing key and `journal-fenced` when the lane is not held or the key is locked by another holder; `withOwnedOrAcquiredLane` reports `journal-fenced` when a retained lane context no longer owns its lock row; opening reports `journal-lease-unavailable` when the process lease cannot be taken; other SQLite failures use `journal-error` and preserve their cause. Reopen with `expectedJournalId` to bind the retained journal; never recreate an absent journal to resume a lane.

Delta records also check parent continuity against the newest ancestor records for each path, or the publication baseline when no earlier record exists. A later record cannot legitimize a stale merge, deletion or restoration. Divergent parallel records require an explicit record of the merge resolution; that choice then constrains descendant records.

## Public API

A plugin composes a purchase from the root names only. Each export's doc comment in `src/index.mjs` names what it returns and what it throws or rejects with; this section lists the factories' methods and the error contract.

The admission option: `admission: { binding, currentLocal }` is required by the three factories below.
- Construction throws `TypeError('admission_required')` without exactly those two members, `TypeError('admission_input_untrusted')` for a `profile`, `record`, `identityRecord` or `actionsAdmitted` option, and `OperationError('runtime_unsupported')` below the Node floor.
- An active method returns a Promise. It rejects `OperationError('profile_not_admitted')` while the hold constant is `held`, or when the binding check fails, with the original error as `cause` (`tp1_authority_timeout` after 10,000 ms). Otherwise it resolves to, or rejects with, the original action's own result or error.
- A passive method keeps its original signature and is never wrapped. `actionsAdmitted` is a construction-time snapshot and never authorizes.

The stop option: `createProtocolPurchases` and `createPurchaseService` take an optional `stopped: () => boolean`, the host's synchronous stop check. Without it, nothing changes.
- Construction throws `TypeError('stop_seam_invalid')` when `stopped` is not a synchronous function. A service given a `protocol` must carry the same function that protocol was built with, or construction throws `TypeError('stop_seam_mismatch')`; a service with no `protocol` may carry its own.
- The check is called on every use and never cached. While it returns `true`, an active method rejects `OperationError('writes_stopped')` before any authority read or write. A check that throws rejects `stop_check_failed` with the error as `cause`; any other answer, including a promise, rejects `stop_check_invalid`. A promise's outcome is never read. `profile_not_admitted` comes first when both apply.
- The same check runs where a seller request is stored, before its pre-send check and at the wire signer, so nothing is signed with the session key and nothing is sent while the host is stopped. A stop that turns on in the middle of a call rejects it with the same `OperationError`, not a `SellerUnavailableError`. The agreement exchange catches seller-client errors, so `agreementSubmit` resolves with an indeterminate agreement note instead of rejecting.
- Passive methods never call it, except `verifyDeal`, which calls it only to decide whether to continue.
- It does not stop wallet effects or the wallet's own signatures; pass the same function to the wallet session. `createDeliveryDeadlineWatch` has no stop check: a stopped host must not start it, or must give it a delivery check that goes through the service.

### Other exports

- The capability constructors `createDemDeliveryContext`, `createNativeDemDeliveryCapability`, `createNativePaymentEvidenceConsumer`, `createSourceDemoSellerTransport` and `createDevnetNativeCommitmentCapability` return a frozen opaque capability and throw `TypeError` for a missing or malformed input. It needs no completed binding, reads the chain through `authority.authorityRpc` and its local evidence on every call, and takes no fence, lock or signer. A connection on another chain answers no decision (`tp1_connection_unverified`); a transport failure rejects with its original error.

- Every other export states its own contract in its doc comment. Failures are the exported error classes (`OperationError`, `NotWiredError`, `OutboundError`, the seller and wallet errors), which keep their cause. ## Public Demos chain reader

`@kynesyslabs/dacs-client/substrate/demos` exports only `createDemosPublicChainReader({rpcUrl, network, pinnedIdentity, timeoutMs, fetchImpl})`. It accepts only `network: 'testnet'` with the 64-hex chain identity pinned for testnet, and otherwise throws `OperationError` `invalid_configuration`. It holds no key and cannot sign or send.

The returned frozen object has nine reads: `readStorageProgram`, `getAddressBalance`, `getTransactionFees`, `networkIdentity`, `getAddressNonce`, `observePurchaseTransfer`, `observeTransfer`, `getTransaction` and `findTransferAtNonce`. It also carries `network`, `pinnedIdentity`, `rpcOrigin`, `observer` and `evidenceMode`. Pass it unchanged as `chain` to `createPurchaseService` and `createListingVerifier` when no native Agreement transport is composed; with one, pass that transport's own `chainReader()` instead.

The first read checks the RPC's chain identity before its own request, and refuses a simulated or different chain with `OperationError` `network_identity_mismatch`. Later reads rely on a successful check, but a read whose answer is marked simulated throws the same error instead of returning it and the next read checks again; a failed check is not reused. Each read otherwise returns and throws what the client's internal reader does, and honours the caller's `signal` where it takes one. `observePurchaseTransfer` reports an included transfer as `{status: 'unavailable', reason: 'native source evidence unavailable from public reader'}`, because this reader keeps no signed native source; a native purchase read through it stays unresolved.

## Node wallet session

`@kynesyslabs/dacs-client/node-wallet` exports `createNodeTransportOwner`, `createNodeObserver`, `createNodeAuthorityCapability`, `createRpcStampSource`, `createHeldTransportFacade`, the TP-1 token functions `admitTp1Authority`, `tp1AuthorityLabel`, `authorityLabelOf` and `isTp1AuthorityToken`, `releaseAbandonedJournalLocks({journal, stateOwnership})`, `passContext` (see the effect gate below), and the asynchronous `createNodeWalletSession`, `composeNodeWalletSession` and `createNodeSellerComposition`. `createNodeAuthorityCapability({owner, claim})` returns the read-only capability the production authority reader uses, `{authorityRpc(body, {signal}), claim(), context(), connectionGeneration()}`, with no sign or send. `authorityRpc` sends only `getBlockByNumber` and `getNetworkInfo` (`readonly_only` otherwise) over the owner's transport, takes no fence, journal lock or signer, limits a reply to 4 MiB before decoding and 1024 entries per array or object after (`authority_list_too_large`), runs at most four reads at once, and gives the reads queued behind them one 10 s deadline (`tp1_authority_timeout`, cause kept). `composeNodeWalletSession` builds the buyer's session in stages from an unopened owner: the capability, the production authority reader, `bindTp1Profile`, the effect boundary, then the session. It also needs `identityRecord`, `listings`, `purchases`, `participantImplementations`, `stopped` and `feeCeilingOs`, makes `admission` itself and returns the session's members plus `binding` and `effectBoundary`; a failed stage leaves no composition. `createNodeObserver({owner, clock})` returns the read-only observer `{observe({signal}), readNodeInfo(message, {signal}), provenance()}`: its expected identity and block-one fallback come only from the SDK-approved TP-1 record, it acquires no connection fence and no journal lock and signs nothing, every node reply is limited to 4 MiB before decoding, each call has one 10 s deadline (`tp1_authority_timeout`) and a caller's abort starts no further read; `readNodeInfo` admits only `getNetworkInfo` and `getNetworkParameters`. Construct the owner on a canonical HTTPS root and bind the SDK-approved TP-1 record to `owner.currentLocal()`. Pass `{admission: {binding, currentLocal: owner.currentLocal}, owner, journal, key, approve, clock, stopped, feeCeilingOs}` (the last two are described below); `key` is UTF-8 mnemonic bytes and is consumed and zero-filled on every outcome. Build the composition before any other import of demosdk.

The returned `wallet.request` is held (`profile_not_admitted`); purchase runtime is Node `^22.22.2 || ^24.15.0`. `getPublicAccount`, `getWriteProfile`, `isLocked` and `lock` remain passive. The synchronous `walletFactory({anchorJournal})` selects a journal for the same wallet identity; it exposes the same held request API. `close()` locks that wallet and closes its transport; the host closes its owner and journal. All SDK posts use the bounded native transport in process. A native broadcast that may have reached the node is never repeated after broadcast intent; restart reads back the original evidence. A broadcast refused at its last check before its request sends nothing; readback answers it `failed` (resolved), and the same signed bytes may go out once through a new lease. Durable pre-confirmation recovery and the owning effect-boundary passes that supply the gate below are prerequisites for lifting the hold.

Before the SDK's inner transaction signature, the session checks synchronously that the signed message is the transaction hash (or, once the node's `signatureDomain` fork is active, `demos-tx:v1:<decimal chain id>:` followed by it), that the hash is the SHA-256 of `JSON.stringify(content)`, and that the SDK's finalized content (amount, fees, edits, and the denomination the node reported at approval) is exactly what was approved, returned as two canonical OS amount strings; otherwise the request fails `payload_mismatch` and nothing is signed. The returned `internalCauseOf(envelope)` gives the host the error a failed request was closed over; its `cause` chain holds the original failure, which the public envelope never carries. `confirm_rejected` means only a validated `valid:false` answer; a malformed, non-200 or unavailable confirmation, or a `valid:true` answer this session cannot match to the approval, is `upstream_unavailable`, and nothing is broadcast after either.

The native transport checks the signature of every transaction it confirms or broadcasts against what the configured node's `getNetworkInfo` says it covers: the bare hash while the `signatureDomain` fork is inactive, `demos-tx:v1:<chain id>:<hash>` once it is active, and no other form. A `getNetworkInfo` answer that cannot be read, or that does not say whether the fork is active (or gives no chain id for an active one), refuses the request with `signature_domain_unreadable` or `signature_domain_malformed` and nothing reaches the node. The answer is kept for one connection only: an active fork is kept, an inactive answer is reused for a minute, and a failed read is tried again on the next request. A request that holds no signature lease reads nothing.

A storage CREATE reads the node (the chain identity, and for a recovery the absence of the transaction and the account nonce) before it asks the node to confirm. Between the confirmation and the broadcast, or the recovery's single resend, the node receives no write and no other confirmation. Only local checks run, plus at most one getNetworkInfo read for the signature-domain check, made only when the kept answer is older than a minute. That read never changes the kept reference block. The confirmation's `reference_block` is kept on the write's lane and intent rows as `storageWriteReferenceBlock`, is replaced only when a recovery reconfirms the exact same bytes, and is handed back as `referenceBlock` on the broadcast result and on a pending `readback`. A confirmation that carries no reference block gives `referenceBlock: null`; it is never filled from a block height. A native transfer keeps and reports none.

The seller composition takes the same options plus required `publications: {settlementPublication, deliveryPublication, demoArtifactPublication}` and `approveConfirmedWrite` (a function in policy mode, an explicit `null` in manual mode; any other value throws `TypeError`). Its session and facade share one transport and journal. It returns the session members plus `transport` (the held facade), `observer` (built from its own owner) and `paymentEvidenceAdapter`. A confirmation by another sender, or of a Listing CREATE, passes without the policy; every other seller confirmation calls it once, and `false` or a throw refuses `approval_required` (a thrown error is kept as `cause`) with nothing broadcast. The policy is asked after the node's acknowledgement is recorded, so the node is not asked to confirm those bytes again; a later confirmation of them in the same operation asks the policy again on the recorded answer. Buyer sessions install no confirmed-write policy. Publication authorities currently need `TEST-` / `TEST-RUN-` declarations; the constructors and publication policies do not yet accept a TP-1 token.

Every composition has one effect gate and a host contract for it. The gate runs at the transaction-hash signature inside `NodeDemos.sign` and at every `confirmTx` or `broadcastTx` body sent through the owner's fetch, the transport's recovery included; RPC-authentication signatures and read bodies pass through. After the SDK's own preparation awaits, one gate pass awaits `qualify` (seller only, when installed), then the pass's `refreshAuthority`, then its `finalStop`, each within the pass's remaining deadline. A result after the deadline refuses. Then, in the same synchronous run, it checks the hold, `currentLocal()` against the binding's local, the connection generation `qualify` returned against the current one, the pass's fence lease, each of its `synchronousChecks` (one that returns a promise refuses), and at the signature the finalized content and debit, with only the finalized fees (`feeDebitOs`, not the amount) compared to the pass's own `feeCeilingOs` from `effectPass` (equal passes, above it refuses `write-fee-cap`). This per-pass fee cap is separate from the session's `feeCeilingOs`, which caps the amount plus fees. Only then does it invoke the signature or the real fetch. A refusal invokes neither, keeps the failing step's own code (`effect_gate_refused` when its error has none) with its error as `cause`, and at transmission reports `not_dispatched`. Steps refuse by throwing; the gate holds no durable state and acquires no fence.

- `createNodeSellerComposition({..., stateOwnership})`: `stateOwnership` is `{directory, held()}`, the host's proof that it holds the state lock for the directory containing `journal`; without it construction throws `state_ownership_required`. Before returning, the composition removes the lock rows of dead holders from `journal` (never a row of a live handle or holder, never by elapsed time, and it changes no record) and retires every signer reservation that has no signed bytes. `releaseAbandonedJournalLocks({journal, stateOwnership})` is that first half alone, for the host's other client journals in the same directory: it resolves `{released: [lock keys]}` and throws `state_ownership_required` when `held()` is not true or the journal's real path is outside `directory`.
- `createNodeSellerComposition({..., paymentEvidenceApproval})`: the kit's approval ledger for payment-evidence CREATEs, `{prepare, open, reopen, confirm, settle}`; construction throws `invalid_params` unless all five are functions. The composition returns `paymentEvidenceAdapter` with the four members listed below. `signCreate(input, {signal})` resolves `{signedTransaction, txHash, nonce}` and sends nothing. `input` is exactly `{logicalAddress, artifact, writer, artifactKind, jobId, receiptContentHash}`; any other member throws `signer_input_invalid`.
  - `signCreate` runs inside the caller's effect pass and keeps one live write per signer: it throws `signer_lane_busy` while the signer has another reservation or an issued native write on the transport's own lane, and `locked` once the session's wallet is locked.
  - It reads the fee inputs only after the node's chain identity matches the pinned one. It stores its approval request before calling `prepare`, binds the returned id before signing, and stores the signed bytes before returning. The SDK's finalized content, fee and edits are compared with the approved CREATE before the inner signature.
  - The same evidence's stored bytes come back for the same input with no new signature. A changed input throws `signer_lane_busy`: signed bytes are never retired, and only an execution of them frees the signer.
  - Any other failure before the signed bytes are stored (a refused approval, a failed read, a gate refusal, a locked wallet at the signature, a signer failure, an abort) releases the authorization and frees the nonce. A signature that arrives after an abort is dropped.
  - An abort while `prepare` has not settled, or a failed store the read-back cannot decide, keeps the reservation and throws `signer_reservation_uncertain`. A later call for that evidence returns the bytes if the store did commit; otherwise it throws the same until the next construction's recovery retires the reservation.
  - `open(requestText)` resolves null or the one open `{ledgerId, requestText}`, and `settle({ledgerId, requestText}, outcome, reason)` is idempotent for the same outcome and must refuse a settlement whose outcome differs from the one already recorded: the replay check settles a released-or-spent authorization `released` again, and relies on that refusal to tell a spent one.
  - `broadcast({signedTransaction, txHash}, {signal})` runs in an effect pass, signs nothing and dispatches the held bytes at most once per call, with no retry. It refuses `retained_transaction_invalid` unless the reservation holds exactly these bytes. It reopens the stored authorization by id. If the ledger no longer holds it open, it first reads the chain for the held bytes the way `readTransactionState` does: an execution ends the reservation and refuses `transaction_already_executed`, and any answer other than the chain saying it has not seen the hash refuses `approval_required`; both send nothing, so an authorization that an execution spent is never replaced by a second one, also after a restart. Even when the chain says it has not seen the hash, an id the ledger shows spent is not replaced (`approval_required`, nothing sent), because that answer may be stale. A manual authorization has no id, so every broadcast reads the chain for the held bytes first. Otherwise it uses the exact request's open authorization or asks for a new one, and the reservation stores that id before anything is sent. It then checks that the node serves the pinned chain (a refusal sends nothing) and sends `confirmTx` with the exact projection. A confirmation that is not a valid answer for those bytes is `outcome_unknown` and sends nothing more; a valid refusal is `confirm_rejected`. `confirm(binding, validity)` runs on every call, and `false` or a throw is `approval_required` with the authorization still held. The send runs under the signer's reservation lock, which a native write holds while it issues and a readback holds to end the reservation. Under that lock the reservation must still hold these bytes, else `retained_transaction_invalid` with nothing sent. Any failure after `broadcastTx` starts is `outcome_unknown`. Both transmissions carry fresh authentication headers from the wallet's stamp source and pass the effect gate.
  - `readAccountNonce({signal})` resolves the account nonce. `readTransactionState({signedTransaction, txHash, nonce}, {signal})` resolves `{state: 'applied'}` only when the node's chain identity is authenticated and the executed transaction is in a block that lists the hash, with the same signature and complete content as the held bytes, and the node serves the storage program the CREATE made (its address, data, metadata, program name and owner, and creation provenance that names this CREATE in both members or in neither). The seller journal passes the bytes and nonce it keeps, so a CREATE whose reservation has ended still reads back; given only `{txHash}`, it uses the bytes the reservation holds for that hash. It then ends the reservation that holds them and settles its authorization `spent` by id; when the ledger refuses the spend and no longer holds the authorization open (an operator released it), the reservation ends without a settlement. Everything else, including a failed execution and any failed or aborted read, is `{state: 'pending'}`, with the cause available from `internalCauseOf`. It never answers `absent`, so a kept CREATE is never superseded by this adapter. Each node reply is limited to 4 MiB and 10 seconds.
- `createNodeWalletSession({..., stopped, feeCeilingOs})` and `createNodeSellerComposition`: the host's stop check `stopped()` and its fee ceiling `feeCeilingOs` (a positive decimal OS amount) are required, with no defaults; a missing or malformed one throws `TypeError` before anything is opened. The session's `feeCeilingOs` caps the whole debit of each paid write, the amount plus every fee, not the fees alone: the signature lease and the confirmation check the amount, and the broadcast checks the amount plus the confirmed fees (`write-fee-cap`, nothing sent). The session builds the client's effect boundary from them over the admitted binding, the journal and the owner's connection fence, gives it to its native transport (which requires one), and returns it as `effectBoundary` next to the held `transport` facade. On the buyer composition a pass made without a `context` is a plain pass; the seller composition takes only a pass with a job context and refuses a pass without one `effect_pass_invalid`, before anything is signed or sent. A job context, which the host that owns the job makes with `passContext({operationClass, operationId, currentAuthorization})` (exported by this subpath), carries the job's class and its current-authorization check; that check runs with the boundary's dispatch checks, before the broadcast's lane and intent records are written (a job withdrawn by then is withheld and leaves the wallet's lane free), at the transport's last check, and again in the gate's synchronous run right before the request. Any other `context` is refused `effect_pass_invalid`.
- `createNodeSellerComposition({..., qualify})`: `qualify({phase, signal})` is absent or a function that resolves the connection generation (its `connectionId`) it observed; anything else, and any `qualify` on the buyer composition, throws `invalid_params`.
- `effectPass({fence, deadline, refreshAuthority, finalStop, synchronousChecks, feeCeilingOs})` returns a frozen handle registered to this composition, and authorizes nothing by itself. It throws `effect_pass_invalid` unless `fence` is a live lease from this composition's own transport owner, `refreshAuthority` and `finalStop` are functions that take `{phase, signal}`, `synchronousChecks` is an array of functions that take `{phase}`, `deadline` is a number on the composition's `clock` between now and 10,000 ms ahead, and `feeCeilingOs` is a canonical positive OS string.
- `runInEffectPass(handle, work)` runs `work` with `handle` as the current pass and returns its result; a `work` that is not a function throws `invalid_params`. While `work` runs, a fence acquisition on the exported transport owner shares the pass's fence and is granted at once (its release frees nothing), so the transport's own steps do not wait on the fence the pass holds. The seller composition refuses `effect_pass_required` when no pass is current, and any composition refuses `effect_pass_invalid` for a handle it did not make (a copy, another composition's), or whose lease is no longer live. The buyer composition runs without a pass; no request field, environment value or per-call option supplies or disables a step.
- `withheldReopen` has two members, for the trusted composition only: the held `transport` facade, the wallet and a wallet relay carry neither. It is the explicit request that sends a retained native transaction whose whole dispatch history shows no possible transmission, once, under the job owner's pass context; it also reaches one whose lane and intent rows were left at `broadcast-started`, which a new lease refuses. `register({operationId, lane, hash, operationClass, currentAuthorization})` returns a one-use capability for the retained native transaction `hash` that operation signed on wallet lane `lane` (`reopen_scope_invalid` for a malformed scope); `operationClass` and `currentAuthorization` are the job owner's private pass context (as for a job pass), run again at the broadcast's last check. `reopen({capability, signRpc})` runs the lease, confirmation and broadcast of that transaction's own retained bytes and takes no transaction; it restores the retained `confirm-acknowledged` answer when the last confirmation was acknowledged, and otherwise confirms again. The capability is consumed by its first pass, whether that refuses or transmits (`reopen_capability_invalid` for an unknown or used one). A transaction whose history shows an acknowledged, unknown or unpaired dispatch, or any recovery, held or observed record, or whose lane or intent row holds a broadcast answer, stays readback-only for good. So does a transaction that was never sent but that a readback later marked failed because another transfer used its nonce. `reopen` also refuses when the history is missing, conflicting or incomplete; when the transaction has an intent row, or a lane row that names it, and the two rows do not both name it, or they conflict, one at `broadcast-started` and the other finished as withheld (a readback finishes a lane left at `broadcast-started` next to a withheld intent row as withheld too); and when the lane row names another unfinished transfer. Each of these refusals is `outcome_unknown` with the cause and sends nothing. When the transaction has no intent row and the lane row is absent or holds another, finished transfer, as when a broadcast was withheld before its rows were written, the history alone decides, and one that shows no possible transmission is sent.
- The TP-1 token: `admitTp1Authority({binding, currentLocal})` resolves a frozen token after the wire's binding check under 10 s; `tp1AuthorityLabel(binding)` returns `TP1-` plus 32 hex digits of `binding.recordDigest`; `authorityLabelOf(value)` returns a token's label or a canonical label unchanged and throws `authority_unbound` otherwise; `isTp1AuthorityToken(value)` is a boolean. A token authorizes nothing by itself and a label string is not a token.

## Seller transport composition

`createSourceDemoSellerTransport({authority, sessionSignerFor, sessionPolicyFor, endpointProofFor})` takes three functions of the purchase: the session signer `{claim, sign}`, the expiry policy `{expiresAt}` and the endpoint proof that the wire's `verifyEndpointProof` returned (verified with the buyer's own commitment receipt reader). The authority still needs a `TEST-` label.

`createSellerAgentClient({url, authentication, ...})` reaches a loopback endpoint, or, when it is given a wire authentication, a public HTTPS origin: `https://` and an authority, with no credentials, path prefix, query or fragment (the wire's `isPublicEndpoint`). Any other `url` throws before anything is signed or sent. Purchase actions are still refused while the release gate holds them.
Requests, delegation bytes and received response bytes go through `@kynesyslabs/dacs/wire` under the purchase's kept TP-1 profile. The client saves the delegation payload before it returns the wallet message, stores the wallet signature as canonical base64url, and refuses a purchase prepared under the old transport declaration with `seller_transport_changed`. The seller request timeout also bounds the wire's authority reads and the session signer: a seller call that has not finished signing by then sends nothing and fails with cause `timeout`, and a wallet message or delegation check that is still waiting for the authority fails with `seller_authority_timeout`.
Payment and bundle requests (the wire's continuing routes) and the two ordinary read routes (`agreements/state`, `bundles/buyer-copy`) of a committed purchase are signed with the job's finalized commitment, its two-party Agreement and the signed Listing, as canonical bytes rebuilt from the purchase row. The commitment's anchored tuple is kept with its SHA-256 when the commitment verifies. A verified row with no usable kept bytes keeps them once from a fresh authenticated readback that matches the stored summary, and otherwise nothing is signed (`commitment_unverified`). The proof's receipt reader authenticates the commitment at every signing, so these requests sign under a `ready: false` proof and after the Listing's window ends, with no continuation capability. Challenge, context, proposals and commitment requests carry no commitment evidence, and a read before commitment keeps the wire's live Listing checks. `bundles/buyer-copy` has no such read before commitment, so the wire refuses it without evidence.

### Seller answer classification

With an authentication adapter, each answer is verified on its exact received bytes, then classified by its HTTP status and `error` code, the route, and the request's provenance. The transport builds the record `{status, signed: true, body}` only after verification; an answer that fails verification is `unknown`. A `result` or `progress` answer is returned. Every other class throws: `definite` and `failed-bootstrap` as `SellerRefusedError` (`code` is the seller's code), the rest as `SellerUnavailableError` (`answerCode` is the seller's code). Both carry `answerClass`. Each seller route stores its exact request bytes under the purchase revision (`state.protocol.sellerRequests`) before the first send; the two read routes store nothing. An authenticated call with a stored attempt retries an unknown dispatch at most twice, 5 seconds apart, using the same bytes and fresh wire nonces. Legacy callers and unrecorded reads send once. One absolute deadline (15 seconds by default; context 240–300 seconds) includes storage, authority reads, signing and fetch; an exhausted budget signs and sends nothing further. Unknown outcomes remain unknown, and a later explicit call reuses stored bytes. Failures before dispatch clear only their own attempt; swallowed failures retain their bounded class and cause. Without an adapter (loopback fixtures only), answers are not classified: a 4xx other than 408 or 429 with an `error` code is `SellerRefusedError`, any other non-2xx answer is `SellerUnavailableError`, and a 2xx body is returned.

A verified `seller_stopped` answer (class `suspended`), a re-hold and a host stop (`writes_stopped`, `stop_check_failed`, `stop_check_invalid` or `stop_check_timeout` as `cause`) seen while work is queued durably record `state.protocol.sellerSuspension: {id, cause, path, at}`. Retries and queued continuations stop, the outcome stays unknown and a dispatched payment is never marked failed. The record and the stored request bytes survive restart and every later save, and re-admission alone resumes nothing. `verifyDeal` keeps its readback and bookkeeping but does not continue a suspended purchase. The protocol view exposes the suspension. To resume, make a new explicit `protocolRecheck({operationId, token, resumeSuspensionId})` request with the suspension's `id`: it checks admission and buyer access again, then clears only the suspension it names, so an older request cannot clear a newer stop. Do not pay again.

## Factory integration

Supply application inputs through host, including a synchronous operations-store factory. On a fresh database, apply the schema, construct the purchase store first, then prepare all statements (reads as well as writes). Existing databases need application-owned migrations preserving the schema constraints. Use the same connection for operation and coordinate writes.

```js
import { DatabaseSync } from 'node:sqlite';
import {
  PURCHASE_STATE_SCHEMA, createSqlitePurchaseStore, createCoordinateStore,
  createProtocolPurchases, createPurchaseService, createDeliveryDeadlineWatch,
} from '@kynesyslabs/dacs-client';

const db = new DatabaseSync(':memory:');
db.exec(PURCHASE_STATE_SCHEMA);
const store = createSqlitePurchaseStore();
const ops = host.createOperations(db);
const coordinates = createCoordinateStore({ db });
const protocol = createProtocolPurchases({
  db, ops, coordinates, store, dacsProtocol: host.dacsProtocol,
  buyerAccess: host.buyerAccess, admission: host.admission,
});
const purchases = createPurchaseService({
  db, ops, coordinates, store, protocol, config: host.config, admission: host.admission,
  accounts: host.accounts, verifier: host.verifier, chain: host.chain,
  challenges: host.challenges, purposes: { APPROVE_PURCHASE: 'purchase-approval' },
});
const watch = createDeliveryDeadlineWatch({ db, ops, coordinates, store, enabled: true });

store.transaction(db, () => {
  ops.transition(host.operation.id, host.operation.status, host.operation.status, {
    state: { hostNote: 'local bookkeeping' }, event: 'host_bookkeeping', data: {},
  });
  coordinates.save(host.coordinate);
});
const diagnostic = purchases.status(host.accountId, host.operation.id, host.token);
```

The synchronous `store.transaction` commits both writes or rolls both back on an error. Nested synchronous calls use savepoints. Keep transaction control, database configuration and schema changes outside callbacks; asynchronous callbacks and results refuse. Call diagnostics outside the transaction. This example records host bookkeeping and grants no purchase or settlement authority.

### Database admission

Use main and TEMP only; detach all other schemas before a package transaction. Admission is checked again on every transaction, before the callback. Persistent files require WAL with synchronous FULL or EXTRA, or a rollback journal with EXTRA. Configure foreign keys and a bounded busy timeout outside the transaction.

- `purchase_store_persistent_attachment`: a file-backed attachment is present.
- `purchase_store_unsupported_attachment`: another attachment, including an in-memory attachment, is present.
- `purchase_store_unsupported_journal_mode`: main has an unsupported journal mode, including OFF or a persistent MEMORY journal.
- `purchase_store_unsupported_synchronous`: a persistent main database lacks the required durability setting; SQLite defaults are insufficient.
- `purchase_store_unsupported_temp_journal_mode`: TEMP has an unsupported journal mode, including OFF.

### Schema

The required schema objects are supplied by `PURCHASE_STATE_SCHEMA`; the application owns initialization and migrations.

The `job_id` column of `operations` and its unique index `operations_job_id_unique` reserve each protocol purchase's job id when the host's `createIdempotent` writes it to `job_id`; keep both when extending the schema (purchases without a protocol job store NULL). `createPurchaseService` generates the id inside the create transaction and passes it to `createIdempotent` as jobId. Construction refuses with code schema_migration_required when `operations` has no `job_id` column or no unique index on `job_id` alone; a partial unique index does not count. The reservation also depends on the host's `createIdempotent` writing jobId to `job_id` in the same insert as the terms, which the package cannot check; it must throw an `OperationError` with code job_id_collision when the index refuses the id. The service then retries with a new id, at most 3 attempts, and otherwise fails with code job_id_unavailable having written nothing.

### Chain reader

For legacy and native purchases alike, provide `network`, `pinnedIdentity`, `networkIdentity` and `observePassiveTransfer`. Network identity resolves the configured identity and mode. The passive reader observes the saved hash without journal reconciliation. Missing or noncallable passive readers produce unavailable readback. It returns one object with these primitive fields:

| Field | Presence | Contract |
| --- | --- | --- |
| `status` | always | `included`, `pending`, `not-found`, `failed`, `invalid` or `unavailable` |
| `reason` | optional | text of at most 240 characters |
| `txHash` | included | the requested hash: 64 hex characters, with an optional `0x` prefix |
| `payer` | included | readable Demos address of at most 66 characters |
| `payee` | included | readable Demos address of at most 66 characters |
| `amountOs` | included | text matching `OS_INTEGER`: canonical decimal integer in OS units, at most 78 digits |
| `blockNumber` | included | nonnegative safe integer; an observation without it is malformed |
| `includedAt` | optional | for included observations, integer epoch milliseconds from 0 to 8640000000000000 |
| `sourceDisposition` | optional | exactly `included` or `failed` |

The fields marked included are required when status is included; other statuses need no transfer fields. Omitted or undefined optional fields are absent. Unknown fields are ignored. Any other shape yields `status` `malformed` with a `reason`. `termsMatch` compares payer, payee and amount; it is null unless the observation is included with no `sourceDisposition` or with `included`. Repeated readback leaves operation and coordinate state unchanged and cannot establish settlement.

### Operations

`ops` is synchronous, returns fresh hydrated operations, preserves original errors and uses the same database connection. Diagnostics use only `get`, `getByHandoff` and `history`. The additional `transition` method is used only by `watch.observe`; it must compare the saved status and atomically update state and append its event, refusing a stale status.

### Diagnostics

The public diagnostics are `status`, `portalOperation`, `portalEvidence` and `verifyDeal`. They authenticate the operation's handoff capability on every call, project elapsed approval windows without saving a transition, and return historical state or non-authoritative observations. Readback uses only the saved transaction hash. It cannot authorize payment, settlement or delivery.

### Protocol

The protocol pass-through methods are exactly `assertBuyerAccess`, `supportsMode`, `readIssued`, `readIssuedPayment` and `observeReportedPayment`. Methods outside this list refuse with `profile_not_admitted` before host effects. No caller option lifts the action hold.

### Writers

The writer list is exactly `watch.observe`: host bookkeeping that cannot establish settlement. It can record a host's not-present delivery observation against an already verified payment; the saved status stays unchanged.
